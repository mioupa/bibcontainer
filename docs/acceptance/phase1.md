### 3.2 測り方

- ダミー DB は、コアの API（`create_books` など）で作った（5 章）。`HOME` を scratchpad に向けて起動した（本物の DB・ログ・書影には触っていない）。
- **起動から一覧の表示まで**: プロセスを exec する直前の時刻（T0）から、Rust の起動ログ（`run()`・`setup`・DB を開いた時刻）と、WebView の JS が打った記録（JS の開始、一覧の行が DOM に出た時刻、その 2 フレーム後）まで。ファイルのキャッシュは温かい状態。Finder やドック経由の起動（LaunchServices）は測っていない。
- **検索**: JS から `search_books` を呼んで、結果の本文を読み終わるまで（`fetch` の時間。IPC を含む往復）。あわせて、検索欄に値を入れる操作を JS で行い、結果が画面の DOM に反映されるまで。Rust 側は、コマンドと同じ経路（`Database::run`）で呼んだ時間と、JSON にする時間。
- **スクロール**: 一覧のスクロール欄を JS で動かし（1 フレームに 8・60・200px を 6 秒ずつ、全冊を通す 1 回）、フレームの間隔（`requestAnimationFrame`）と、メインスレッドの詰まり（4ms のタイマーの遅れ。50ms 以上の長いタスクの数も）を見た。
- **メモリ**: アプリ本体と、その起動の直後に増えた `com.apple.WebKit.GPU`・`WebContent`・`Networking` を対象にした。WebKit のプロセスは、起動の前後で一覧を取り、アプリの PID より新しいものを選んで特定した（アプリを止めると 3 つとも終わることを確認）。値は macOS の `proc_pid_rusage`（`ps -o rss` と同じ常駐サイズ = RSS と、物理フットプリント）を 1 秒ごとに読んだ。RSS は共有ライブラリのページと、解放済みでまだ OS に返っていないヒープも含むため、Activity Monitor の「メモリ」に近い物理フットプリントも併記する。
- 画面がロックされると WebView が止まるため、そのあいだは JS を使う計測（スクロールと UI の検索）ができない。計測の途中でロックされたので、2 万冊のスクロールと UI の検索は測れていない（2 万冊の検索は Rust 側で測った）。

### 3.4 評価と気づいた点（改善前。2026-10-14）

| 項目 | 目標 | 結果 |
|---|---|---|
| 起動から一覧まで | 2 秒以内 | 満たす（5,000 冊で約 0.66 秒、2 万冊でも 1.35 秒） |
| 検索 | 100ms 以内（2 万冊で 300ms 以内） | 満たす（5,000 冊で反映まで最大 37ms、2 万冊でコマンドは最大 15ms） |
| スクロール | 60fps 目安 | 測れる範囲では詰まりなし。60fps は C01（この Mac の画面は 30Hz） |
| メモリ | 300MB 以下 | **RSS 合計では未達**。物理フットプリントではアイドルで満たし、書影を数千冊ぶん表示すると未達 |

気づいた点（アプリの変更はしていない。判断はユーザーに任せる。→ 1・2・4 は 2026-10-15 に対応した。3.5）:

1. **メモリ**。一覧用のサムネイルが、枠の約 4 倍の長辺（160px）で、デコード済みのまま保持されている。一覧（`sm`）だけ長辺 80px 前後のサムネイルを作る（`THUMBNAIL_SIZES` に足す）と、増え方は約 4 分の 1 になる見込み。判断が要るのは、「300MB」を RSS の合計で見るか、物理フットプリントで見るか。→ **物理フットプリントで判定する**ことになり、80px のサムネイルを足した。ただし、効いたのは 80px ではなく、WebKit のメモリキャッシュに残さないこと（0010 §14、3.5）。
2. **日次バックアップが DB の接続を塞ぐ**。日次バックアップは起動の約 5 秒後に、接続（1 本を Mutex で共有）を持ったまま `VACUUM INTO` を行う。5,000 冊で約 0.3 秒、2 万冊で約 1.2 秒（`sqlite3` で測定）のあいだ、一覧の取り直しや検索が待たされる。1 日に 1 回だけで、通常は気づかない長さ。→ 別の読み取り専用の接続で取るようにした（0006 §12、3.5）。
3. **初回の `list_books` が遅い**。起動時の 1 回目は、2 回目以降の約 6 倍（5,000 冊で 75ms と 12ms、2 万冊で 320ms と 47ms）。起動時間のうち 2 万冊では約 0.3 秒を占める。→ 0003 の `VACUUM` で DB のページが並び直ったので、移行した DB では、起動から一覧まで 5,000 冊で約 0.5 秒、2 万冊で約 0.7 秒に縮んだ（3.5）。原因（初回の読み込みの遅さ）自体は調べていない。
4. **DB が大きい**。5,000 冊で 63MB、2 万冊で約 250MB（1 冊あたり約 12.6KB。`field_clocks` と索引で 42MB、`outbox` で 10MB）。項目ごとの時計（FR-SYNC-05）の保存費用で、いまのところ性能には響いていない（バックアップの時間は上の 2）。→ `field_clocks` を `WITHOUT ROWID` にして約 3 割小さくした（0006 §11、3.5）。
5. **`HOME` を変えても、WebKit の管理データは本物のフォルダに書かれる**。`~/Library/WebKit/io.github.mioupa.bibcontainer/WebsiteData/` の `ResourceLoadStatistics` などが更新された（アプリの DB・ログ・書影・設定は、変わっていないことを確かめた）。

### 3.5 性能改善後の再計測（2026-10-15）

3.4 の気づいた点のうち、メモリ（1）、バックアップが接続を塞ぐこと（2）、DB の大きさ（4）を直して、同じ Mac で測り直した（5,000 冊と 2 万冊のダミー DB は同じもの）。対象は、`ec3a333` の作業ツリー（コミット前）。直した内容は、0006 §11（`field_clocks` を `WITHOUT ROWID` にするマイグレーション 0003）、0006 §12（バックアップを別の読み取り専用の接続で取る）、0010 §14（一覧のサムネイルを長辺 80px にし、`size=80` の応答を `no-store` にする）。

**測り方（3.2 との違い）**

- [ ] **C25 ISBN 一覧の取り込み**（FR-IO-03）: ISBN と 2段目が混ざったテキストファイルを読み込むと、追加した冊数・重複の冊数・読み取れなかった行の数が通知される。

## 5. ダミー DB の作り方と、本物の DB を壊さない試し方

ダミーの蔵書（既定 5,000 冊）と書影を、コアの API で作るプログラム `docs/acceptance/dummy-db` を使う（アプリのビルドとは無関係。ワークスペースの外）。すでに `library.sqlite3` があるフォルダには何も書かない。macOS で、fish のコマンド。

```fish
# プログラムをビルドする（初回だけ。20 秒ほど）
cargo build --release --manifest-path docs/acceptance/dummy-db/Cargo.toml

# 作業用の HOME を作り、その下のアプリのデータフォルダに、ダミー 5,000 冊（書影 5,000 種）を作る（20 秒ほど）
set DUMMY_HOME (mktemp -d)
set DATA_DIR "$DUMMY_HOME/Library/Application Support/io.github.mioupa.bibcontainer"
docs/acceptance/dummy-db/target/release/dummy-db $DATA_DIR 5000 5000

# HOME を向けてアプリを起動する（本物の DB・ログ・書影には触らない）
env HOME=$DUMMY_HOME target/release/bundle/macos/bibcontainer.app/Contents/MacOS/bibcontainer
```

- 引数は `<データフォルダ> [冊数] [書影の種類の数] [乱数の種]`。2 万冊で試すなら `... $DATA_DIR 20000 500`。書影の種類を減らすと、早く作れる（既定は 500）。
- 開発モードで試すなら、最後の行を `env HOME=$DUMMY_HOME pnpm tauri dev` にする。
- 終わったら、アプリを閉じて `rm -rf $DUMMY_HOME`（ダミーの DB・ログ・書影・サムネイル・バックアップが消える）。
- 本物のデータは `~/Library/Application Support/io.github.mioupa.bibcontainer/` にあり、この手順では触れない。ただし、WebKit が自分の管理データ（閲覧統計など）を `~/Library/WebKit/io.github.mioupa.bibcontainer/` に書くのは、`HOME` を変えても止められない（アプリの DB・ログ・書影・設定ではない）。
- 登録・編集の確認（C06〜C27、C33、C41）は、ダミーのデータの上で行う。ダミーの本の書影は、色つきの図形だけの画像。
- Windows のデータフォルダの切り替えは確かめていない（`HOME` のような環境変数では切り替わらない可能性が高い）。Windows で本物のデータがあるときは、試す前に `%LOCALAPPDATA%\io.github.mioupa.bibcontainer\` をフォルダごとコピーして退避しておく。
