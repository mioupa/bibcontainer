# 0013: フェーズ2の同期の設計

## 状態

採用

## 日付

2026-10-15

## 背景

フェーズ2では、同期フォルダ（主に Google Drive for desktop）を介して、複数の端末で同じ蔵書を使えるようにする（要件書 7.8、8.3、12 章フェーズ2）。フェーズ0・1で、すべての変更を Op として outbox に記録し（0004）、項目単位の LWW で冪等・順序非依存に適用できるようにしてある。ここでは、Op を同期フォルダに書き出して取り込む仕組み、新しい端末が加わる流れ、画面とのやり取りを決める。

## 決定

### 1. 構成

- 新しいクレート `crates/sync`（`bibcontainer-sync`）に同期エンジンを置く。Tauri に依存しない。コア（`bibcontainer-core`）に依存する。
- 同期フォルダへの読み書きは `SyncTransport` トレイト（FR-SYNC-12）を通す。初版の実装は `LocalFolder`（`std::fs`）。テスト用に、ファイルが遅れて見える・途中まで書かれている・衝突コピーができる、を再現できるメモリ上の実装を用意する。
- トレイトの操作は、一覧（名前・大きさ・更新時刻）、読む、書く（一時ファイルに書いてから名前を変える）、存在確認、自分のファイルの削除、フォルダの作成。
- 書影の本体は、これまでどおり端末ローカルの `covers/` に置き、表示もローカルから行う。同期フォルダの `covers/` は端末間で受け渡すための写し。
- 監視（notify）・定期実行・終了時の書き出しなどの「いつ動かすか」は `src-tauri` が担当し、エンジンは「1 回分の取り込み」「1 回分の書き出し」などの関数を提供する。

### 2. 同期フォルダの構成（8.3 から変えた点あり）

ユーザーが選んだフォルダの下に `bibcontainer-library/` を作る（選んだフォルダ自体が `bibcontainer-library/` で、`library.json` があればそれを使う）。

```
bibcontainer-library/
├─ library.json                         … 作成時に 1 回だけ書く
├─ devices/<device_id>.json             … その端末だけが書く（書き出しのたびに置き換え）
├─ ops/<device_id>/<seq_from:010>-<seq_to:010>.jsonl   … 書き込み後は変更しない
├─ covers/<先頭2文字>/<sha256>.jpg      … 内容で名前が決まるので、どの端末が書いても同じ内容
└─ snapshots/<device_id>/<ms15>-<counter5>.jsonl.gz   … その端末だけが書く
```

- **8.3 からの変更**: スナップショットのファイル名は HLC そのもの（`:` を含む）ではなく `<ミリ秒15桁>-<カウンタ5桁>`。Windows のファイル名に `:` を使えないため。端末 ID はフォルダ名で分かる。
- **FR-SYNC-04 の例外**: `covers/` は全端末が書く。ファイル名が内容の SHA-256 なので、同じ名前なら内容も同じで、上書きしても壊れない。既にあれば書かない。
- `library.json`: `{ "format": "bibcontainer-library", "formatVersion": 1, "libraryId": "<UUIDv7>", "minAppVersion": "0.1.0", "createdAt": "...", "createdBy": "<device_id>" }`。
- `devices/<id>.json`: `{ "deviceId", "name", "os", "appVersion", "lastExportAt", "maxSeq" }`。

### 3. セグメント（Op のファイル）

- 1 行 1 Op の JSON Lines（0004 の形）。最終行は終端レコード `{"end":true,"count":N,"sha256":"<hex>"}`。`sha256` は、終端レコードより前の全行のバイト列（各行の改行 `\n` を含む）の SHA-256 を小文字の 16 進で書いたもの。
- 1 ファイルは最大 1,000 Op。書き出す Op がそれより多ければ、複数のファイルに分ける。
- 書き方: 同じフォルダに `.tmp-<乱数>` で書いてから名前を変える。成功したら outbox の該当行を `flushed=1` にする。名前を変えた後、`flushed` にする前に落ちた場合は、次の書き出しで同じ範囲を同じ内容で書き直す（既に同じ名前のファイルがあり、内容が同じなら書かない）。
- 起動時に、自分のフォルダに残った古い `.tmp-*` を消す。
- 読む対象は `^\d{10}-\d{10}\.jsonl$` に一致する名前だけ。一致しないもの（`… (1).jsonl` などの衝突コピー）は読まずに警告をログに出す。
- 終端レコードがない・件数やハッシュが合わないファイルは、書き込み途中か同期途中とみなし、読まずに次の回に回す（AT-S5）。
- 各 Op の `dev` がフォルダの端末 ID と一致し、`seq` がファイル名の範囲に入っていることを確かめる。合わないものはその Op だけ捨てて警告する。

### 4. 取り込み（1 回分）

1. `library.json` を読み、ライブラリ ID が手元の DB と一致するか確かめる。違えば同期しない（`mismatch`。FR-SYNC-10、AT-S8）。`minAppVersion` がアプリの版より新しければ同期しない（`updateRequired`）。
2. 他の端末ごとに、セグメントの一覧を取る。取り込み済みの範囲（`applied_segments`）で全部覆われているファイルは読まない。
3. 読むファイルは、1 ファイルを 1 トランザクションで適用する: 中の Op の HLC の最大値を `observe_hlc` してから、各 Op を `apply_op` する。適用したら範囲を `applied_segments` に記録する。
4. 時計のずれ（FR-SYNC-11）: 他端末の Op の HLC のミリ秒が、この端末の現在時刻より 5 分以上先なら警告を出す（適用はする）。
5. 知らない `ent` を含むセグメントは、知っている Op だけ適用し、範囲は記録しない（アプリを更新した後に、改めて全部適用されるように）。`v` が 1 より大きい Op も同じ扱い。
6. 書影: 取り込んだ本の `cover_hash` のファイルがローカルになければ、同期フォルダの `covers/` から写す。まだ届いていなければ仮の表紙のまま、次の回に再確認する（届いていない書影の数を状態に出す）。
7. 変わった本の ID を `library-changed` で知らせる。

### 5. 書き出し（1 回分）

1. 未書き出しの Op を seq 順に読む。
2. それらが参照する書影（`cover_hash` の値）を、先に同期フォルダの `covers/` に写す（既にあれば写さない）。
3. セグメントを書き、`flushed=1` にする。
4. `devices/<自分>.json` を書き直す。
- **重複した端末 ID の検出**: 書こうとした範囲と重なる既存のファイルがあり、内容が違うときは、別の端末が同じ端末 ID を使っている（アプリのデータフォルダを丸ごと別の PC に写した、など）とみなし、同期を止めてエラーにする。

### 6. スナップショット

- 形式（gzip した JSON Lines）:
  - 1 行目は見出し: `{"v":1,"kind":"snapshot","libraryId","dev","hlc","covers":{"<device_id>":<seq>,...}}`。
  - 2 行目からは、エンティティごとに 1 行: `{"ent","id","fields":{"<項目名>":[<値>,"<HLC>"],...}}`。項目は `field_clocks` に時計がある項目すべて（ドット付きのキー、`extra_json` の未知の項目を含む）。
  - 最終行は終端レコード（セグメントと同じ規則）。
- `covers` は「この時点で、各端末の Op を seq 1 から何番まで切れ目なく適用したか」。自分の端末は現在の seq。他の端末は `applied_segments` の範囲を 1 から連続している所までたどった値。
- 適用: エンティティごとに、同じ HLC の項目をまとめた Op を作って `apply_op` する（LWW なので、どの状態に重ねても正しい）。適用したら、`covers` の各端末について範囲 `1..=seq` を取り込み済みとして記録する。
- 書く時機: (a) 新しいライブラリを作るとき（手元にデータがあれば）、(b) 既存のライブラリに統合するとき、(c) バックアップから復元した DB が同期を再開するとき、(d) 前回のスナップショットから自分の Op が 2,000 件以上たまったとき、または 7 日以上たって新しい Op があるとき。自分のスナップショットは新しい 2 つだけ残す。
- (a)〜(c) では、スナップショットが手元の全状態を含むので、その時点の未書き出しの Op は `flushed=1` にする（セグメントには書かない）。復元のときに `outbox_restored` に移した Op も、スナップショットに反映済みになるので捨ててよい。
- 新しい端末の最初の取り込み: 取り込み済みの範囲が何もなければ、全端末のスナップショットのうち HLC が最新のものを 1 つ読んで適用してから、残りのセグメントを取り込む（AT-S6）。

### 7. 初めての設定（FR-SYNC-09）と解除

- フォルダを選ぶと、まず中身を調べる（`inspect`）: 空（ライブラリがない）／このライブラリ／別のライブラリ／書き込めない／アプリの更新が必要。
- 空なら「新しいライブラリを作る」: `library.json` を書き、ライブラリ ID を DB（`local_meta`）に記録し、手元にデータがあればスナップショットを書く。
- ライブラリがあり、手元が空なら「参加する」: ライブラリ ID を記録して取り込む。
- ライブラリがあり、手元にデータがあれば、ユーザーが選ぶ:
  - **統合**: ライブラリ ID を記録し、手元の状態をスナップショットとして書き出してから取り込む。両方の本がすべて残る（同じ本が別の ID で 2 冊になることがある、と画面で伝える）。
  - **置き換え**: 手元の DB をバックアップしてから、新しい空の DB（新しい端末 ID）に作り直し、取り込む。
- 手元の DB が既に別のライブラリに属していて、選んだフォルダのライブラリ ID と違う場合は、警告して同期しない（AT-S8）。「同期を解除」してから選び直してもらう。
- **同期を解除**: 同期フォルダの設定、ライブラリ ID、取り込み済みの範囲を消す。手元のデータと同期フォルダの中身はそのまま。
- 同期フォルダの場所は端末ごとの設定（`local_settings` の `sync` セクション）、ライブラリ ID は DB（`local_meta`）に持つ。ライブラリ ID は DB の中身に結びつくため。

### 8. いつ動かすか（`src-tauri`）

- 取り込み: 起動時、ウィンドウが前面に来たとき、ファイル監視の通知（2 秒まとめる）、60 秒ごと（FR-SYNC-06）。
- 書き出し: 最後の変更から 5 秒後（まとめ書き）、終了時（最大 5 秒待つ）、起動時に未書き出しがあれば（FR-SYNC-07）。
- 取り込みと書き出しは同時に走らせない（1 つずつ）。ファイルの読み書きは別スレッドで行い、DB の接続を長く持たない。
- 同期フォルダが使えない（見つからない、権限がない、容量不足）ときは、エラーを状態に出してローカルの操作は止めない（10.2）。

### 9. 状態と画面（FR-SYNC-08）

- 状態 `SyncStatus`（IPC、camelCase）:

```ts
type SyncState = "disabled" | "idle" | "syncing" | "error" | "mismatch" | "updateRequired";
type SyncDevice = {
  deviceId: string; name: string; os: string; appVersion: string;
  lastExportAt: string | null; isSelf: boolean;
};
type SyncStatus = {
  state: SyncState;
  folder: string | null;          // bibcontainer-library のフォルダの絶対パス
  libraryId: string | null;
  deviceId: string;
  deviceName: string;
  lastExportAt: string | null;    // ISO 8601
  lastImportAt: string | null;
  pendingOps: number;             // 未書き出しの Op の数
  missingCovers: number;          // まだ届いていない書影の数
  error: string | null;           // 直近のエラー（日本語）
  clockSkew: { deviceId: string; deviceName: string | null; aheadMs: number } | null;
  devices: SyncDevice[];
};
type FolderInspection = {
  kind: "empty" | "library" | "otherLibrary" | "notWritable" | "updateRequired";
  libraryFolder: string;          // 実際に使う bibcontainer-library の絶対パス
  libraryId: string | null;
  devices: SyncDevice[];
  localHasData: boolean;
  localLibraryId: string | null;
};
type SetupMode = "create" | "join" | "joinMerge" | "joinReplace";
```

- コマンド: `get_sync_status`、`inspect_sync_folder(path)`、`setup_sync(path, mode)`、`leave_sync()`、`sync_now()`、`set_device_name(name)`、`gc_covers()`（FR-SYNC-13）。
- イベント: `sync-status`（ペイロードは `SyncStatus`）。状態が変わるたびに出す。
- 端末名の既定値はホスト名（FR-CONF-01）。
- 上部バーに「同期: ✓ 12:04」のような表示（9.1）。押すと設定の同期の節を開く。
- 設定の同期の節: フォルダの選択と設定の手順（新しく作る／参加／統合／置き換えの説明と確認）、状態、端末の一覧、警告（ライブラリの不一致、時計のずれ、更新が必要）、「今すぐ同期」「同期を解除」、書影の整理、Google Drive の使い方の注意（ストリーミングならオフラインで使用可能にする、など。8.3 の末尾）。

### 10. そのほか

- **自分のセグメントの統合** [SHOULD]: 30 日より古い自分のセグメントを 1 つにまとめ、元のファイルを消す。読む側は取り込み済みの範囲で覆われていれば読まないので、重複して適用されない。
- **書影の整理**（FR-SYNC-13）[SHOULD]: どの本からも参照されていない書影のうち、ファイルの更新時刻が 30 日より前のものを、ローカルと同期フォルダの両方から消す。手動の操作だけ。
- **同期中の復元**: 同期中にバックアップから復元すると、他の端末の変更をもう一度取り込むので、ライブラリ全体が過去に戻るわけではない（手元の DB の修復の意味になる）。画面で伝える。
- Google Drive のストリーミングモードでは、ファイルを読むときにダウンロードが起き、時間がかかることがある。読み取りは別スレッドで行い、1 回の取り込みで扱うファイル数に上限を設けて、残りは次の回に回す。

## 理由

- エンジンを Tauri から切り離すと、複数の端末（DB とフォルダ）をテストの中で模擬でき、AT-S1〜S8 と収束の性質テスト（AT-S7）を速く確実に回せる。
- スナップショットは、項目ごとの時計を含む状態（LWW の状態そのもの）なので、どの状態に重ねても正しい。新しい端末の参加、統合、復元後の再開を同じ仕組みで扱える。
- outbox には phase 0 以降の全変更が残っているが、復元で端末 ID が変わった場合などに欠けがありうる。全状態を書くスナップショットの方が確実。
- 同期フォルダの場所を端末ごとの設定に、ライブラリ ID を DB に持つのは、別の PC では Google Drive のパスが違う一方、ライブラリへの所属は DB の中身の性質だから。

## 影響・今後

- 要件書 8.3 のスナップショットのファイル名を、本記録の形に直す提案をする。`covers/` が FR-SYNC-04 の例外であることも書き足す。
- `outbox` の書き出し済みの行は当面残す（5,000 冊で約 10MB）。スナップショットで覆われた古い行を消すかは、運用を見て決める。
- Google Drive API を直接使う `SyncTransport` の実装（モバイル版向け）はフェーズ4。
