# 0027: 一括再取得（表示中の本をまとめて、裏で進め、途中でやめられる）

## 状態

採用（2026-11-14 にユーザーが設計と受け入れ基準 AT-46〜AT-49 を承認。実装中）

## 日付

2026-11-14

## 背景

FR-META-13（[SHOULD]）の「一括も可」を、フェーズ 3 の 3 番目として作る（0022 §1）。今の「書誌を再取得」（0010 §9）は、選んだ本を `refetch_books` で取り直し、終わるまで IPC の応答を返さない。進み具合は出ず、途中でやめられない。

洋書は 1 冊に数秒かかる（Google は障害の回避策で 3 回（0018）、Open Library は 2 回（0017）。どちらも 1 秒あける）。全件や、サイドバーの絞り込み（取得待ち・情報不足など）の本をまとめて取り直すと、数百冊で数十分になる。そのため、取得元への配慮（Google の Dynamic Links の captcha、Open Library の大量取得の禁止、Google Books API の 1 日の割り当て）が要る。

### 公式の情報の確認（2026-11-14）

| 取得元 | 確認したこと |
|---|---|
| Open Library（https://openlibrary.org/developers/api） | 名乗らない利用は 1 秒に 1 回（メール付きの User-Agent なら 3 回）。「API で書誌を大量にダウンロードしない」「1 冊ずつの問い合わせを何百回もしない（まとめた結果には search.json を使う）」「複数の IP に分散させない」。違反すると強い制限か遮断。数での定義はない |
| Open Library の検索 | `search.json?q=isbn:(A OR B …)&fields=…,editions,editions.isbn,…` で、1 回で複数の ISBN を探せる。4 冊（洋書 3・和書 1）で、各 ISBN の作品と、その ISBN に合う版（`editions.docs`）が返った。1 つの ISBN に別の作品（宣伝の登録）が付くこともある（`9780132350884` に `The Earn2Trade Discount Code`） |
| Google の Dynamic Links（https://developers.google.com/books/docs/dynamic-links） | `bibkeys` はカンマ区切りで複数を書ける（上限は GET の長さだけ）。3 冊（`ISBN:9780132350884,ISBN:9784003101117,ISBN:9784123456784`）で、見つかった 2 冊の項目が `ISBN:<ISBN-13>` で返った。利用の上限は書いていない |
| Google Books API | 1 日の割り当ての数・超えたときの応答は、公式の文書に書いていない（Cloud Console のプロジェクトごとの設定）。今の実装は、`per day` を含む 429・403 を 1 日の上限として扱っている（`classify_failure`） |

## 決定

### 1. 入口

- 一覧の上の帯（CSV の書き出しのボタンの隣）に、**表示中の本をまとめて再取得する**ボタンを置く。表示中の本は、サイドバーの絞り込みと検索の結果（巻をまとめた表示でも、本に広げる）。「すべて」を選べば全件、「取得待ち」「情報不足」を選べばその本になる。ボタンは、アイコンと「再取得…」（読み上げ・ツールチップは「表示中の N 冊の書誌を再取得…」）。ゴミ箱を開いているとき、0 冊のとき、再取得が動いているときは押せない。
- 今の入口（一覧の右クリックの「書誌を再取得…」、詳細ペインの「書誌を再取得」）も、同じ裏の処理（§2）で動かす。経路は 1 つにする。
- 確認のダイアログは今の `RefetchDialog`（「手で直した項目も上書きする」。既定はオフ）に、次を足す。
  - ISBN のない本の数（取得しない）。
  - 10 冊以上なら、時間の目安（1 冊 約 2 秒として「約 M 分」）と、進み具合はステータスバーに出て途中でやめられること。
  - 300 冊以上なら、「取得元の 1 日の上限（Google など）に達すると、そこで止まります。もう一度実行すると、残りから進みます。」

### 2. 裏の処理（再取得の作業）

- 再取得の作業は**同時に 1 つ**。始めるコマンドはすぐ戻り、作業は裏で進む（画面を止めない）。動いている間に始めようとすると `conflict`。取得待ちの自動再取得は、今と同じく見送る（`refetch_lock` の `try_lock`）。登録・スキャン・キーワード検索の取得は、再取得の作業を待たない（取得元ごとの間隔と同時接続の数を共有するので、1〜2 秒遅れることはある）。
- 本は **10 冊ずつ**取得して、まとまりごとに書き込む（今の `CHUNK` は 20。取得待ちの自動再取得も 10 にする）。最初の 1 冊だけで通信できるかを確かめる（0010 §9）のは今のまま。
- 進み具合は、始めたとき・まとまりごと・終わったときに、イベント `refetch-progress` で知らせる。
- **やめる**: すぐ止める。取得中のまとまりは、取得を打ち切って書き込まない（取得は読むだけなので、捨てても DB は変わらない。生の応答のキャッシュに入ったものは、そのまま使える）。書き込みの途中なら、そのまとまりを書き終えてから止める。
- 本ごとの規則は今のまま（0010 §9、0021 §3・§4）: キャッシュを使わずに通信する、手で直した項目は上書きしない（選べば上書き）、2段目由来の Cコード・本体価格を保つ、取得元が返さなくなった値を消す（`clear_stale`）、使えない形の書影を取り直す。書き込みは本ごとのトランザクションで Op を記録し、まとまりごとに `library-changed` を出す（同期の書き出しは最後の変更の 5 秒後なので、長い作業の間は数十秒ごとに書き出される）。

### 3. 取る順番: 前回の取得が古い本から

- 生の応答のキャッシュ（`provider_cache`）の取得日時で並べる。本ごとの値は、使う取得元（通信するもの）の行の `fetched_at` のうち**いちばん古いもの**。行のない取得元があれば、取ったことがないとみなして先頭に来る。同じ値なら渡された順。ISBN のない本・見つからない本は、すぐ終わるので先頭でよい。
- こうすると、途中で止まった（やめた・制限・オフライン）あと、同じ絞り込みでもう一度実行すると、取れなかった本から進む。Google の 1 日の上限で、毎回同じ本で止まって先へ進まない、を防ぐ。新しい状態（残りの一覧など）は持たない。
- 制限で取れなかった取得元は、キャッシュの行が古いままなので、その本は次の実行で先に来る。

### 4. 取得元への配慮（上限と間隔）

1. **間隔**: 今のまま。取得元ごとに 1 秒に 1 回、同時に 1 つ（`ProviderRateLimit`）。Open Library の公式の上限（名乗らない利用は 1 秒に 1 回）に合う。
2. **Open Library の検索をまとめる**（`supports_batch` を真にして `fetch_raw_batch`）。
   - 10 冊ずつ、`search.json?q=isbn:(A OR B …)&fields=<今と同じ>&limit=100` で 1 回。結果を ISBN ごとに分け、その ISBN（13 桁、978 なら 10 桁も）を `editions.docs[].isbn` に含む作品だけを、返った順に入れた検索の応答（`{"numFound": n, "start": 0, "docs": [...]}`）を作る。あとは 1 冊のときと同じ（版の JSON を取り、`{"search": …, "edition": …}` に包む。0017 §2）。キャッシュ・解析・結果の形は 1 冊ずつのときと同じ。
   - 応答が `limit` で切れていて（`numFound` が返った作品の数より多い）、見つからなかった ISBN は、1 冊ずつの検索で取り直す（取りこぼして「該当なし」にし、`clear_stale` で値を消さないため）。
   - 版の JSON（ページ数・内容紹介）は、今どおり見つかった本だけ 1 回ずつ。和書はほとんど収録がないので、ほぼ 0 回。書影は書影 ID で取る（制限なし）のも今のまま。
   - 1 冊だけのとき（登録など）は、今の 1 冊の流れ（`run_provider` は 2 冊以上のときだけまとめる）。
3. **Google の Dynamic Links をまとめる**（`supports_batch` を真にして `fetch_raw_batch`）。
   - 検索（`volumes?q=isbn:`）は 1 冊ずつ（Books API にまとめる方法はない）。検索で該当なしだった本を 10 冊ずつ、Dynamic Links に `bibkeys=ISBN:A,ISBN:B,…` で 1 回で問い合わせる。各 ISBN の項目（`ISBN:<ISBN-13>`）から ID を取り、`volumes/<ID>` は 1 冊ずつ（0018 §1 のとおり ISBN を確かめる）。項目のない ISBN は該当なし。「唯一の項目を使う」（0018 §1）は、1 冊だけ問い合わせたときだけにする。
   - Dynamic Links のエラー（captcha の 429 など）は、そのまとまりの本すべての Google のエラーにする（キャッシュされない。今と同じ意味）。
   - 障害の間、Dynamic Links への問い合わせが 10 分の 1 になる。1 冊にかかる時間は、検索と `volumes/<ID>` の約 2 秒になる。
4. **制限を返されたら、残りを問い合わせない**（取得のすべてに効く）。取得元が **401・403・429**（429 はリトライのあと。1 日の上限はリトライしない。0010 §13）を返したら、その取得元には、その呼び出しの残りの本を問い合わせず、同じ状態（HTTP の番号とメッセージ）にする。`run_provider` の 1 冊ずつの流れと、`fetch_raw_batch`（Open Library・Google。Dynamic Links の 403・429 も）の両方で行う。
5. **再取得の作業は、制限を返されたら止める**。まとまりの取得のあと、取得元の結果に 401・403・429 がある本は書き込まず（未処理として残りに数える）、ほかの本は書き込んで、作業を止める（理由: 取得元の名前・HTTP の番号・メッセージ）。書き込まないのは、Google の値が順位の低い取得元の値に置き換わり、取得状態が「一部取得」に下がるのを防ぐため。取得待ちの自動再取得は、今のまま（取れた値は書く。止めない）。
6. **通信が切れたら止める**: まとまりの取得がすべて通信エラーなら、そのまとまりは書き込まず、作業を止める（理由: オフライン）。今の「残りを `offline` として返す」の代わり。
7. **1 回の冊数の上限は設けない**。2・3 で問い合わせが少なくなり、4・5 で制限のところで止まり、§3 の順番で次の実行が続きから進むため。Google Books API の 1 日の割り当ては数が分からないので、冊数では切らず、上限の応答で止める。

目安（Google の回避策が要る間）: 1 冊 約 2 秒（Google の検索と `volumes/<ID>` が律速）。500 冊で約 17 分。Google を使わなければ NDL の 1 秒が律速。

### 5. IPC とイベント

```rust
// src-tauri（ts-rs で src/bindings/ に出す。u64 は bigint になるので使わない）
#[serde(rename_all = "camelCase")]
pub enum RefetchJobState { Running, Finished, Cancelled, Stopped }

#[serde(tag = "kind", rename_all = "camelCase")]
pub enum RefetchStopReason {
    Cancelled,
    Offline,
    Limited { provider: String, status: u16, message: String },
    NoActiveProviders,
    Error { message: String },
}

#[serde(rename_all = "camelCase")]
pub struct RefetchJobStatus {
    pub job_id: u32,          // 1 から。起動ごとに数え直す
    pub state: RefetchJobState,
    pub override_manual: bool,
    pub total: u32,           // 重複を除いた冊数
    pub done: u32,            // 済んだ冊数（updated + unchanged + offline + skipped + failed）
    pub updated: u32,
    pub unchanged: u32,
    pub offline: u32,
    pub skipped: u32,
    pub failed: u32,
    pub covers_saved: u32,
    pub kept_manual_fields: u32, // 手で直したので書かなかった項目の数（AT-16）
    pub remaining: u32,          // total - done（止まったときは未処理の冊数）
    pub stop_reason: Option<RefetchStopReason>, // state が Cancelled・Stopped のとき
    pub elapsed_ms: u32,
}
```

| コマンド | 内容 |
|---|---|
| `start_refetch(ids, overrideManual)` → `RefetchJobStatus` | 作業を始めて、すぐ戻る（`state: running`）。動いていれば `conflict`。使える取得元がなければ、すぐ `stopped`（`noActiveProviders`）で終わる |
| `cancel_refetch()` → `null` | 動いている作業をやめる。なければ何もしない |
| `get_refetch_job()` → `RefetchJobStatus \| null` | 今の作業、または最後に終わった作業（画面を開き直したとき用） |

- イベント `refetch-progress`（`RefetchJobStatus`）。始めたとき・まとまりごと・終わったとき。
- 今の `refetch_books` コマンドは消す（経路を 1 つにする）。`RefetchSummary`・`RefetchItem` は、作業の中とテストで使うなら残してよい。

### 6. 画面

- **ステータスバー**: 動いている間、「書誌を再取得中 37 / 412 冊・残り約 12 分」と細い棒、「やめる」ボタン。残りの時間は、それまでの速さ（`elapsedMs / done`）から出す（`done` が 0 の間は「残りを計算中」、1 分未満は「残り 1 分未満」）。
- **終わったとき**: 通知（toast）を出す。
  - 終わった（`finished`）: 今の `describeRefetch` と同じ要約（更新・変化なし・通信できず・飛ばした・失敗、手で直して残した項目の数）。
  - やめた（`cancelled`）: 「再取得をやめました。N 冊済み・残り M 冊」に要約を添える。
  - 止まった（`stopped`）: 理由（「Open Library が制限を返しました（HTTP 429）」「Google の 1 日の上限に達しました」「通信できなくなりました」など）と、済んだ・残りの冊数と、「もう一度実行すると、残りから進みます」。閉じるまで残す。
  - 通知は、作業ごとに 1 回（`jobId` で見分ける）。
- 動いている間、ほかの再取得の入口（右クリックの「書誌を再取得…」、詳細ペインの「書誌を再取得」、帯のボタン）は押せない。
- ブラウザのモック（`pnpm dev`）では、作業を時間で進めるまねをする（見た目の確認用）。

## 理由

- 表示中の本を対象にしたのは、サイドバーの絞り込み（すべて・取得待ち・情報不足・タグ・保管場所…）と検索をそのまま使えて、CSV の書き出し（`exportShown`）と同じ考えで分かりやすいため。専用の対象の選び方を作らない。
- 経路を 1 つにしたのは、1 冊の再取得も、まとめての再取得も、同じ規則（止め方・順番・配慮）で動くようにするため。
- 冊数の上限より、まとめた問い合わせと「制限で止める」「古い順に取る」を選んだのは、上限の数に根拠がない（Google の割り当ては分からず、Open Library の「大量」は数で決まっていない）ため。Open Library が勧める形（search.json でまとめる）に合わせ、Google の captcha のもとになる Dynamic Links の回数を減らすほうが、取得元への配慮として筋がよい。
- 制限で止めた本を書き込まないのは、§4 の 5 のとおり、値の質と取得状態を下げないため。自動再取得は、取得待ちの本を取れた値で埋めるのが目的（キーが無効でも NDL の値で埋まる）なので、今のままにした。
- 進み具合を 10 冊ごとにしたのは、まとめた問い合わせ（10 冊で 1 回）と、書き込みの単位に合わせるため。1 冊ごとに知らせるには取得の層に知らせの仕組みが要り、その割に効き目が小さい（10 冊で約 20 秒）。
