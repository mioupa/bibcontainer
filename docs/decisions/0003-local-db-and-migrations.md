# 0003: ローカル DB とマイグレーション

## 状態

採用

## 日付

2026-10-14

## 背景

要件書は、SQLite を同期フォルダに置かず端末ローカルに持つこと（0 章 5、FR-SYNC-03）、WAL モードで更新をすべてトランザクションにすること、スキーマ変更はマイグレーションで行い適用前に自動でバックアップを取ること（10.2）を求めている。フェーズ 0 では、この土台を `crates/core` に作る。

## 決定

- **置き場所**: DB は端末ローカルに置く。コアは `open(db_path, backup_dir)` で受け取るだけで、パスは Tauri のアプリデータフォルダなどを使ってアプリ側が決める。親ディレクトリがなければ作る。
- **PRAGMA**（接続ごとに設定）: `journal_mode=WAL`、`synchronous=FULL`、`busy_timeout=5000`。
- **外部キー制約は作らない**。同期対象テーブル（books / series / locations / tags / shelves）の間でも、`field_clocks` などとの間でも張らない。
- **マイグレーション**: `PRAGMA user_version` で版を管理する。SQL は `crates/core/migrations/NNNN_名前.sql` に置き、`include_str!` で `MIGRATIONS` に登録する。版は 1 からの連番で、並びが違えば `InvalidMigrations`。ランナーの `migrate(conn, &[Migration], backup_dir)` は一覧を引数に取るので、テストではダミーの一覧を使える。
- 各マイグレーションは 1 つの即時トランザクションで実行し、`user_version` の更新も同じトランザクションに入れる。失敗したらロールバックされ、版は変わらず、`MigrationFailed` を返す。SQL に `BEGIN` / `COMMIT` は書かない。
- **適用前バックアップ**: 未適用があり、DB が新規でない（`user_version > 0`）場合だけ、`VACUUM INTO` で `backup_dir/pre-migration-v{旧版}-{UTC:%Y%m%dT%H%M%SZ}.sqlite3` に保存する。同じ秒に再試行して名前が重なるときは `-1`、`-2` と連番を付ける。新規 DB と適用なしのときは作らない。
- **版が新しすぎる場合**: DB の版がアプリの最新版より大きければ、`Error::SchemaTooNew { found, supported }` を返す。DB には何も書かず、バックアップも取らない。
- **0001_init.sql**: 要件書 8.2 をもとにする。変更点は `0004-hlc-and-op-log.md` に書く。`books_fts` と `book_tags` は入れない。
- `open` は、マイグレーションのあとで端末 ID がなければ作る（`0004` 参照）。

## 理由

- WAL は要件 10.2。`synchronous=FULL` にするのは、WAL で `NORMAL` だと電源断のときに直近のコミットを失う可能性があるため。このアプリは書き込み頻度が低く、FULL の遅さは問題にならない。
- `busy_timeout` は、将来、同期エンジンや書影の処理が別の接続を開いたときに、すぐ `SQLITE_BUSY` にならないようにするため。
- 外部キーを使わないのは、他端末の Op が順不同で、欠番を挟んで届くため（8.3）。たとえば本の `location_id` が、まだ届いていない保管場所を指すことがある。外部キーがあると、その Op を適用できないか、適用順を強制することになり、「どの順でも同じ結果になる」という設計と両立しない。参照先が見つからないときの扱いは、読む側（アプリ）で決める。
- `user_version` は追加のテーブルが要らず、DDL と同じトランザクションで更新できる。SQL ファイルを埋め込むので、配布物に別ファイルが要らない。
- `VACUUM INTO` は、要件 FR-IO-05 のバックアップと同じ手段で、WAL でも一貫したスナップショットが取れる。
- 版が新しすぎる場合を専用のエラーにするのは、アプリ側が「読み取り専用で起動して更新を促す」といった分岐をできるようにするため。
- `books_fts` と `book_tags` は `tags_json` などから作る派生の索引。正規化（NFKC、ひらがな→カタカナ、小文字化）や、Op の適用時に更新するかどうかの設計が検索の実装と一体なので、フェーズ 1 で検索と一緒に決める。派生なので、あとからマイグレーションで追加して再構築できる。bundled の SQLite で FTS5 の trigram トークナイザが使えることだけ、テストで確認した。

## 影響・今後

- マイグレーションを足すときは、`migrations/` に新しい番号の SQL を作って `MIGRATIONS` に追加する。適用済みのファイルは編集しない。
- 古い `pre-migration-*.sqlite3` を消す処理は、このクレートにはない。日次バックアップの世代管理（FR-IO-05）と一緒に、フェーズ 1 で考える。
- 「版が新しすぎるときは読み取り専用で開く」API は、まだない。今は `open` がエラーを返すだけ。
- `open_in_memory` はテスト用で、WAL にならず、バックアップも取らない。
- `rusqlite` は `bundled` 機能で SQLite 自体をビルドするので、ビルド環境に C コンパイラが要る。Windows のビルドは CI で確認する。
