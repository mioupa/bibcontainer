# 0006: コアのデータ層（書籍の操作・検索・書き出し・バックアップ）

## 状態

採用

## 日付

2026-10-14

## 背景

フェーズ 1 のうち、`crates/core` に置くデータ層を実装した。範囲は、取得元・手修正の記録の同期キー（0005 §1）、検索と並べ替えのための派生データ（0005 §6）、一覧の行（0005 §4）、書籍・保管場所・タグ・シリーズの操作、CSV・JSON の書き出し、バックアップと復元（0005 §2）である。0005 が決めた層の間の取り決めの中身と、実装で決めたことをここに記録する。

## 決定

### 1. 取得元と手修正の記録（0005 §1 の実装）

- 書籍の Op のキーは `field_sources.<項目名>`（取得元の文字列か null）と `manual_fields.<項目名>`（`true` か null）。項目全体のキー `field_sources`・`manual_fields` は廃止し、`Entity::Book.fields()` からも外した（Op に来ても知らない項目として `extra_json` に入るだけ）。
- `<項目名>` は書籍の既知の項目名に限る。ローカルの記録（`record_change`）では不正なら `InvalidOp`。リモートの適用（`apply_op`）では警告を出して無視し、`ApplyOutcome::invalid` に数える（時計も進めない）。値の型（取得元は文字列か null、手修正は `true` か null。`false` は不正）が合わないときも同じ。
- ドット付きのキーは、そのまま `field_clocks.field` に入る。時計に勝ったときだけ、`books.field_sources_json`（キー辞書順のオブジェクト。null でキーを削除）と `manual_fields_json`（項目名の辞書順の配列。null で除去）を更新する。項目ごとの勝者が同じなら、適用の順序や重複によらず同じ保存形式になる（収束テストにこれらのキーを含めた）。
- `dump_canonical` は、書籍に `field_sources`（オブジェクト）と `manual_fields`（配列）を出す。時計はドット付きのキーで出る。
- 記録を付ける項目は、外部から取得する書誌の項目（`values::TRACKED_FIELDS`: ISBN、書名・ヨミ・副書名、シリーズ ID・巻次、著者、出版社、発行日、Cコード、NDC、価格、ページ数、大きさ、言語、内容紹介、書影）に限る。読書記録・購入情報・所有状態・保管場所・タグ・メモなど、利用者が持つ項目は、由来が何でも値だけを書く（記録を付けると Op が増えるだけで、再取得の保護に関係しないため）。

### 2. 値の由来（origin）の規則

項目の変更は「値」と「由来」の組（`FieldChange`）で受ける。由来は `Manual`、`Barcode`、`Import`、`Provider(名前)`。

| 由来 | 動作 |
|---|---|
| `Manual` | 値を書き、`field_sources.<f> = "manual"`、`manual_fields.<f> = true` を同じ Op に入れる。現在の値と同じなら何も書かない（フォームが変えていない項目を送っても、手修正にならない）。 |
| `Provider`・`Barcode`・`Import` | その項目が手修正済みなら書かない（`skippedManual` に入る。FR-META-07、AT-16）。`UpdateOptions::override_manual` のときだけ書き、`manual_fields.<f> = null` を入れる。書いたら `field_sources.<f> = 取得元名`（`barcode`、`import`、`openbd` など）。値が空（null、空文字、空の配列）のときは何もしない（取得できなかった項目で、既にある値を消さない）。手修正でなく、値も取得元の記録も既にあるなら、同じ値の再取得では Op を作らない。 |

- 取得元の名前に空文字と `manual` は使えない。
- 作成は、全項目を `set` に入れた Op を 1 つ書く（未指定の項目は、NULL 可なら null、それ以外は既定値）。値が空でない書誌の項目には、同じ Op に由来の記録を入れる。ID は UUIDv7、`created_at` は ISO 8601 UTC ミリ秒。
- 規則（`update_book_in` と `create_book_in`）: 読書状況が `read` に**変わった**とき、読了日が空なら今日を入れる（FR-READ-02）。所有状態が `wanted` から `owned` に変わるとき、購入日が空なら今日を入れる（FR-SCAN-18）。同じ変更で日付を指定したときは、その日付を使う。「今日」はローカルタイムゾーンの日付で、`Env::with_today` でテストから差し替える。
- 巻次の並べ替え用の数値（`volume_sort`）は、巻次（`volume`）から作る（`volume::volume_sort`。`巻1`・`第12巻`・`Vol.3`・`巻一`・`第十二巻`・`上`/`中`/`下` など。読み取れなければ `None`）。`create_book_in` と `update_book_in` は、巻次を書くときに同じ変更へ `volume_sort` が明示されていなければ、作った値を同じ Op に入れる（由来は巻次と同じ）。
  - 作成: 読み取れなければ入れない。更新: 読み取れなければ `volume_sort` を null にする（古い数値を残さない）。`volume_sort` を明示した変更（null を含む）は、その値が優先。
  - 更新で巻次が実際に書かれたときだけ作る。同じ巻次の保存や、手修正済みで書かれなかった取得元の巻次（`skippedManual`）では、数値も作らない（組になる項目は一緒に扱う）。手入力の巻次なら、数値にも手修正の記録が付く（あとで取得元の値が数値だけを上書きしない）。
  - 以前は書誌取得側（`src-tauri/src/metadata/volume.rs`）だけが作っていた。コアに移し、書誌取得側はコアの関数を使う。
- 検証（ローカルの変更）: `ownership`・`read_status`・`wish_priority`・`purchase_cond`・`meta_status` の列挙値、`rating` は 1〜5、日付（発行日・読み始めた日・読了日・購入日）は `YYYY`／`YYYY-MM`／`YYYY-MM-DD`（実在する日付）、`isbn13` は 13 桁でチェックデジットが正しいこと（ハイフン・全角は直してから検べる。ISBN-10 は受け付けない）、`c_code` は 4 桁の数字、金額とページ数は 0 以上。全角を半角にする、前後の空白を除く、空白だけの文字列を null にする、タグの重複を除く、といった正規化をしてから保存する。`series_id`・`location_id` は存在する（削除していない）ものだけ。`created_at`・`deleted`・`purged` は `update_book` では変えられない（専用の操作を使う）。
- ゴミ箱（`deleted = true`）、復元（`deleted = false`）、完全削除は専用の関数。既にその状態の本は飛ばし、変えた本の ID を返す（アプリが `library-changed` を出すため）。

### 3. 完全削除の扱い

- `purged = true`、`deleted = true` にし、`created_at` を除く内容の項目をすべて既定値（NULL 可なら null）に戻す。取得元・手修正の記録（`field_sources.*`、`manual_fields.*`）も null にする。1 つの Op で行う。行は残る（他端末に削除を伝えるため）。
- 完全削除した本は、一覧（`list_rows`）・検索・書き出し CSV・重複チェックに出ない。JSON 書き出しには（空の項目のまま）出る。復元と項目の変更はできない（`Conflict`）。

### 4. マイグレーション 0002 と派生データ

`0002_local_settings_and_search.sql`（0001 は編集していない）で次を作る。すべて端末ローカルで、同期しない。

| テーブル | 内容 |
|---|---|
| `local_settings(key, value_json)` | 端末ごとの設定（`settings` モジュールで読み書き）。 |
| `book_idx(idx, book_id, sort_title, sort_authors)` | 書籍 1 冊につき 1 行。`idx` が `books_fts` の rowid。並べ替えキーを持つ。 |
| `books_fts` | FTS5（`tokenize='trigram'`）。列は `title, title_kana, authors, publisher, series, tags, memo, isbn`。 |
| `book_tags(book_id, tag)` | `tags_json` から作る索引。タグの件数と名前の変更に使う。 |
| `outbox_restored(dev, seq, hlc, op_json)` | 復元したバックアップの outbox に残っていた未書き出しの Op の退避先（§8）。 |

あわせて `books(series_id)`、`books(location_id)` に索引を足した。

- `books_fts` には、`normalize_for_search`（§5）をかけた文字列を入れる。`title` は書名＋副書名、`authors` は著者の名前とヨミ、`tags` は空白で連結、`isbn` は ISBN-13 と（`978` 始まりなら）ISBN-10 を空白で連結したもの。副書名と著者のヨミを検索対象に入れたのは、要件書に明記はないが、利用者が画面で見る書名に含まれる語、ヨミで探したい語だからである。
- 更新は `apply_op` の後処理（`derived::after_apply`）で行う。書籍の検索に関わる項目（ISBN、書名、ヨミ、副書名、シリーズ ID、著者、出版社、タグ、メモ、`purged`）が変わった本と、派生データの行がまだない本を作り直す。シリーズの `name` が変わったら、そのシリーズの本をすべて作り直す。他端末の Op を取り込んだときも同じ経路で更新される。完全削除した本は外し、ゴミ箱の本は残す。
- 全体の作り直しは `derived::rebuild`。`open`（`open_with_migrations`、`open_in_memory`）が、マイグレーションの後に `derived::ensure_built` を呼ぶ。`local_meta` の `derived_version` が `DERIVED_VERSION` と違えば作り直す（0002 を適用した直後、正規化や列の構成を変えたとき）。
- 一覧の並べ替えキーは `book_idx` に持つ。無いとき（作り直しの前）は `list_rows` がその場で作る。

### 5. 正規化と検索

- `normalize_for_search(s)`: NFKC → 英字の小文字化 → カタカナ（`ァ`〜`ヶ`、`ヽ`・`ヾ`）をひらがなに。長音符はそのまま。`unicode-normalization` クレートを使う。
- `search_books(conn, query)`: 検索語を正規化して空白（全角を含む）で区切り、語ごとに「書名・ヨミ・著者・出版社・シリーズ名・タグ・メモ・ISBN のどれかに含まれる」を AND で組み合わせる。3 文字以上の語は FTS5 の MATCH（語を二重引用符で囲んだフレーズにするので、演算子や記号は文字として扱われる）、2 文字以下の語は同じ列に対する `LIKE`（`%` `_` `\` はエスケープ）。結果は ID 順（登録順）で、ゴミ箱の本を含み、完全削除した本を含まない。検索語が空なら全冊。
- ISBN: ハイフンを除いた 13 桁はそのまま、正しい ISBN-10（ハイフン入りを含む）は ISBN-13 に直して照合する。それ以外のハイフン入りの語（`2001-2010` など）は触らない。チェックデジットの計算は `normalize` モジュールに小さく書いた（`barcode` モジュールには依存しない）。

### 6. 一覧の行と詳細

- `ListRow`（形は 0005 §4 のとおり）、`Author { name, kana, role }`、`BookDetail`（同期する全項目＋`fieldSources`＋`manualFields`＋`extra`）は `#[derive(Serialize, TS)]`、`camelCase`、`#[ts(export)]`。`list_rows` は完全削除したもの以外の全件を ID 順で返す（ゴミ箱の本は `deleted: true`）。`get_rows(ids)` は指定した順で返し、存在しない ID と完全削除した ID は結果に含めない（呼び出し側は「要求したのに無い」ものを一覧から外す）。
- `sortTitle` はヨミがあればヨミ、なければ書名を正規化したもの。`sortAuthors` は先頭の著者のヨミ（なければ名前）を正規化したもの（著者がなければ空）。
- 列挙値は、他端末から未知の値が届いても、画面に渡す型（TypeScript の文字列リテラルの組）を壊さないよう、読み出し時に既定値へ直す（`ownership` は `owned`、`readStatus` は `unread`、`metaStatus` は `ok`、`wishPriority` は null）。著者の壊れた要素は捨てる。

### 7. 書籍以外の操作

- 保管場所: 作成（親の下の末尾）、名前の変更、親の変更（自分自身・子孫の下へは `Conflict`）、並び順（`reorder_locations(親, ID の並び)`。挙げなかった兄弟は今の順で後ろに続く。変わったものだけ Op を書く）、削除（子の保管場所か本がある間は `Conflict`。本にはゴミ箱の本も数える）。一覧は親が子より先に来る深さ優先で、パス（`自宅 > 書斎の本棚 > 3段目`）と深さを付ける。2 台が同時に親を入れ替えて循環ができても、親が見つからなくても、一覧から消えず、止まらない（ルートとして末尾に並べる）。
- タグ: 一覧は名前・件数（ゴミ箱の本を除く）・色。本のないタグでも tag エンティティがあれば載る。名前の変更は、名前が完全に一致するタグだけが対象（`研究` を変えても `研究/SiC` は変わらない）。該当する本すべての `tags` と tag エンティティを 1 つのトランザクションで書き換え、変更先に同名のタグがあれば 1 つにまとめる（本の `tags` は重複を除き、tag エンティティは変更先の方を残して古い方を削除）。同じ名前の tag エンティティが複数あるときは ID が最小のものを使う。名前の変更では、同じ名前のエンティティすべてを扱う（先頭を改名し、残りは削除）。色の設定は、最小 ID のエンティティに書く（無ければ作る）。複数の本のタグの一括変更（`modify_tags`: 足す・外す）も足した。
- シリーズ: `find_or_create_series` は、正規化した名前が一致する削除していないシリーズのうち ID が最小のものを返し、無ければ作る。名前の変更、一覧（ヨミ順、ゴミ箱の本を除く冊数つき）。
- 購入店の候補は使用回数の多い順（同数は名前順）。取得待ちの本の ID は、`meta_status = 'pending'` で、ゴミ箱でも完全削除でもないもの。
- 重複チェック `find_by_isbn` は、ハイフンと ISBN-10 を許し、ID・書名・所有状態・保管場所 ID とパス・ゴミ箱かどうかを返す（ゴミ箱でない本、所有・欲しい本・手放した、登録順）。

### 8. バックアップ・復元（FR-IO-05、0005 §2）

- 作成は `VACUUM INTO`。作成途中は `.<名前>.tmp` に書いてから名前を付け替える。アプリは、アプリの接続とは別に開いた読み取り専用の接続（`backup::open_reader`）で実行する（§12）。
- ファイル名（`backup_dir`。UTC）:

| 種類 | 名前 | 世代 |
|---|---|---|
| 日次 | `daily-YYYYMMDDTHHMMSSZ.sqlite3` | 新しい 7 つ |
| 週次 | `weekly-YYYYMMDDTHHMMSSZ.sqlite3` | 新しい 4 つ |
| 手動 | `manual-YYYYMMDDTHHMMSSZ.sqlite3` | 消さない |
| 移行前 | `pre-migration-v{版}-YYYYMMDDTHHMMSSZ.sqlite3`（`migrate` が作る） | 消さない |
| 復元前 | `pre-restore-YYYYMMDDTHHMMSSZ.sqlite3`（と `-wal`） | 消さない |

  同じ秒に重なったときは `-1`、`-2` を付ける。
- `run_scheduled_backup` は、最後の日次から 24 時間以上たっていれば（または日次がなければ）日次を作り、最後の週次から 7 日以上たっていれば（またはなければ）その日次のコピーを週次として残し、ローテーションする。時期でなければ何もしない（呼び出しは起動時と 1 時間ごとでよい）。ローテーションの失敗は警告にとどめる。
- 復元 `restore_backup(バックアップ, DB のパス, 退避先のフォルダ, 時計)`。呼び出し側は接続をすべて閉じてから呼ぶ。
  1. バックアップを DB の隣の作業用ファイル（`<DB 名>.restore-tmp`）にコピーして検証する（開ける、`integrity_check` が `ok`、版が 0 でない、版が新しすぎない（`SchemaTooNew`）、`books`・`local_meta`・`outbox`・`field_clocks` がある）。失敗したら現在の DB には何もしない。
  2. 古い版なら、作業用ファイルをマイグレーションで最新にそろえる（バックアップは取り直さない）。
  3. **新しい端末 ID を振り、`op_seq_last` を 0 に戻す**。HLC の前回値は残す。
  4. outbox は空にし、未書き出し（`flushed = 0`）の Op は、古い端末 ID を付けて `outbox_restored` に移す。outbox は seq が主キーなので、seq を 1 から振り直すと、古い端末の行と重なって次の変更の記録が失敗するため。この Op をどうするかはフェーズ 2 で決める（0005 §2 のとおり）。
  5. 今の DB（と `-wal`）を `pre-restore-…` として残す。
  6. 今の DB の `-wal`・`-shm` を消してから、作業用ファイルを DB のパスに置き換える（古い WAL が新しい DB に重なって壊すのを防ぐ）。
  復元した DB は `open` で開き直す（古い版のバックアップなら、派生データは `open` が作る）。
- `verify_backup` は、コピーを作って同じ検査をする（元のファイルは変えない）。`list_backups` は新しい順に種類・時刻・大きさを返す。

### 9. 書き出し（FR-IO-01、FR-IO-02）

- CSV: UTF-8 の BOM（`EF BB BF`）付き、改行 CRLF、`,` 区切り。`,`・`"`・改行を含む欄は `"` で囲み、`"` は `""` にする。ヘッダーは日本語の項目名。列は次のとおり（1 冊 1 行）。

  `ID`、`ISBN`、`書名`、`書名のヨミ`、`副書名`、`シリーズ`（名前）、`巻次`、`巻次（並べ替え用）`、`著者`、`出版社`、`発行日`、`Cコード`、`NDC`、`本体価格`、`参考税込価格`、`ページ数`、`大きさ`、`言語`、`内容紹介`、`書影`（ハッシュ）、`所有状態`、`欲しい本の優先度`、`保管場所`（パス）、`タグ`、`読書状況`、`読み始めた日`、`読了日`、`評価`、`感想`、`購入日`、`購入店`、`購入価格`、`新品・中古`、`購入メモ`、`メモ`、`取得状態`、`ゴミ箱`（`はい` か空）、`登録日時`

  著者は `名前（役割）` を `; ` で連結（役割がなければ名前だけ）、タグも `; ` で連結する。列挙値（所有状態・優先度・読書状況・新品中古・取得状態）は日本語の表示名で書く。取得元・手修正の記録と未知の項目は含めない（JSON に含まれる）。対象の ID を渡すと、その ID の本だけを渡した順に書く（存在しない ID・完全削除した ID は飛ばす）。渡さないときは完全削除していない全冊を登録順に書く（ゴミ箱の本を含む）。ファイルへの書き出しは、同じフォルダの一時ファイルに書いてから名前を付け替える。
- JSON: 先頭のキーが `format`（`bibcontainer-library`）、`version`（`1`）、続いて `exportedAt`、`schemaVersion`、`deviceId`、そして `books`・`series`・`locations`・`tags`・`shelves`。各要素は `{ "id", "values", "extra", "clocks" }` で、`values` は Op 上の項目名と値（書籍は `field_sources` のオブジェクトと `manual_fields` の配列を含む）、`extra` は知らない項目、`clocks` は項目ごとの HLC（`field_sources.<項目名>` などドット付きのキーも）。ゴミ箱の本・完全削除した本を含む全エンティティ。読みやすいよう整形して書く。

### 11. DB のサイズとマイグレーション 0003（2026-10-15 追記）

| 内訳（5,000 冊、0002 の DB） | 大きさ | 割合 |

| `books`（本体 4.6MB と索引 0.7MB） | 5.3MB | 8% |
| 検索（`books_fts_*`） | 2.9MB | 5% |
| `book_idx`・`book_tags` と、その索引 | 1.6MB | 2% |

1 冊あたり `field_clocks` が約 50 行（書誌の項目ごとに 1 行）で、1 行は約 93 バイト（`entity` 4 + `entity_id` 36 + 項目名 約 12 + `hlc` 36）。通常のテーブルは、行の本体と主キーの索引の両方に `(entity, entity_id, field)` を持つので、同じキーが 2 回入っていた。

**`0003_field_clocks_without_rowid.sql`**（0001・0002 は編集していない）:

- `field_clocks` を `WITHOUT ROWID` のテーブルに作り直す。新しいテーブルを作り、主キーの順に写し、古いものを消して名前を付け替える。列・主キー `(entity, entity_id, field)`・値は同じ。同期の形式、Op、HLC の比較、`dump_canonical` には触れない（0004 のとおり）。主キーの B 木が行の本体を兼ねるので、キーは 1 回だけになる。
- 古いテーブルの領域は、DB のファイルの空きページとして残るだけで、ファイルは縮まない。そこで、`migrate` が、マイグレーションを適用したあとに、**空きページが 1,000 ページ以上で、かつファイルの 2 割以上を占めるときだけ `VACUUM` する**（`reclaim_space`。マイグレーションのトランザクションの外で、すべて適用したあとに 1 回。続けて `wal_checkpoint(TRUNCATE)` で WAL を空にする）。失敗しても警告だけで、マイグレーションは成功のまま。復元で古い版のバックアップをそろえるとき（`migrate_without_backup`）にも同じ処理が働く。`VACUUM` で rowid が変わりうるが、rowid を参照する表は `INTEGER PRIMARY KEY`（`book_idx.idx`、`outbox.seq`）で、変わらない。
- 移行前のバックアップ（`pre-migration-v2-…`）は、これまでどおり適用の前に取る。

結果（この Mac の SSD、リリースビルド）:

|---|---|---|
| DB のファイル（0002 → 0003） | 63.3MB → **44.3MB**（−30%） | 252.1MB → **176.2MB**（−30%） |
| `field_clocks`（本体 + 索引 → 本体のみ） | 43.1MB → 24.3MB | 約 172MB → 約 97MB |
| 0003 の適用（移行前のバックアップを除く）＋ `VACUUM` | 約 0.15 秒 ＋ 約 0.16 秒 | 約 0.58 秒 ＋ 約 0.63 秒 |
| 0002 → 0003 で初めて起動したときの `open` 全体 | 約 0.63 秒 | 約 2.5 秒 |
| 新しい版で最初から作った DB（`VACUUM` なし） | 47.4MB | — |
| バックアップ 1 世代（`VACUUM INTO`。日次・週次・手動とも） | 61.1MB → 44.3MB | 243.4MB → 176.2MB |
| 日次 7 + 週次 4（11 世代）の合計 | 約 670MB → 約 490MB | 約 2.7GB → 約 1.9GB |

- 縮み方は、5,000 冊でも 2 万冊でも同じ（約 3 割）。1 冊あたりでは、約 12.6KB → 約 8.8KB。
- テスト（`crates/core/tests/migrate.rs`）: 0002 の DB に本を入れてから 0003 を適用し、`field_clocks` の全行と `dump_canonical`（全エンティティ・全時計）が変わらないこと、主キーの列と順が同じで `rowid` を持たないこと、移行前のバックアップが版 2 のまま残ること、適用後も時計の更新（`ON CONFLICT … DO UPDATE`）と新しい変更の記録が動くこと、空きページが多いときは `VACUUM` でファイルが縮み、空きページが残らず `integrity_check` が `ok` なこと。収束の性質テスト（`convergence.rs`）、Op の適用・記録・復元のテストは、新しいテーブルのまま通る。

調べたが行わなかった縮小:

- **`outbox`（10.3MB、5,000 冊の約 23%）**: 書き出し済みの行を消せば縮むが、書き出す側（同期エンジン）はフェーズ 2。Op の JSON の形は変えない。
- **`field_clocks` の残り（24.3MB、約 55%）**: 1 行 93 バイトのうち `entity_id` と `hlc` が 36 バイトずつ。同じ本の項目は、作成や取り込みで同じ HLC を共有することが多く、`entity_id` は 1 冊で約 50 回繰り返される。行を本ごとにまとめる、HLC を短い表記にする、といった形の変更は、時計の比較（0004 の文字列比較）と `dump_canonical`、フェーズ 2 の取り込みに影響する。同期の形に触れずにできる範囲を超えるので、フェーズ 2 で `outbox` を整理したあとの大きさを見て、必要なら再検討する。
- 検索（`books_fts`、2.9MB）、`books`、`book_tags` は小さく、削る理由がない。バックアップの圧縮も、復元と検証の経路が増えるので行っていない。

### 12. バックアップを別の接続で取る（2026-10-15 追記）

日次バックアップ（`VACUUM INTO`）は、アプリの接続（`Database` の Mutex で共有している 1 本）を持ったまま走り、5,000 冊で約 0.2 秒、2 万冊で約 0.8 秒のあいだ、検索・一覧の取り直し・保存を待たせていた。WAL なので、読み取りと書き込みは別の接続なら並行できる。

- コア: `backup::open_reader(db_path)` は、DB を**読み取り専用**で開く別の接続（`SQLITE_OPEN_READ_ONLY`、`busy_timeout` は 5 秒）。`create_backup`・`manual_backup`・`run_scheduled_backup`（`_keeping`）は、これまでどおり `&Connection` を取るので、この接続を渡す。`VACUUM INTO` は 1 つの読み取りトランザクションなので、**始まった時点のスナップショット**になる（実行中に別の接続が commit した保存は、含まれるか含まれないかのどちらかで、途中の状態にはならない）。書き込めない接続なので、誤って DB を変えることもない。設定（保存先・世代数）の読み出しも、この接続で行う。
- アプリ（`src-tauri/src/database.rs`）: `Database::run_backup(|読み取り専用の接続| …)` を足した。接続の Mutex は、DB を開けているかを確かめる間（一瞬）しか持たず、`f` の間は持たない。DB を開けていないときは、`run` と同じく保持しているエラーを返す。日次バックアップ（`backups::start_scheduler`）と手動バックアップのコマンド（`manual_backup`）が、これを使う。`list_backups`・`restore_backup` が設定を読む部分は、これまでどおり `run`（一瞬）。
- **復元との排他**: バックアップの接続は DB のファイルを直接開くので、復元（ファイルの置き換え。`-wal`・`-shm` を消す）と重なってはいけない。`Database` に `backup_gate`（Mutex）を足し、`run_backup` は実行の間これを持ち、`restore` は最初にこれを取る（取る順は、門 → 接続の Mutex）。復元は実行中のバックアップが終わるまで待ち、復元の間はバックアップが始まらない。バックアップどうしも、重ならない（一時ファイル名が同じ秒に重なるのを避ける）。ふつうの `run` は門を取らないので、バックアップにも復元の待ちにも巻き込まれない。
- 起動の 5 秒後に最初のバックアップを取る待ち（0009 §6）は、接続の取り合いを避けるためのものだったが、今は接続が別なので、ディスクと CPU が重ならないための待ちになった。そのまま残した。
- 終了時の `wal_checkpoint(TRUNCATE)`（`Database::checkpoint`）は、バックアップの読み取りが走っている間は、`busy_timeout` まで待つ。

テスト:

- コア（`crates/core/tests/backup.rs`）: 読み取りの接続で完全なバックアップ（`integrity_check` が `ok`、WAL にだけある書き込みも含む）が取れて、日次の自動実行も動くこと、書き込めないこと。別のスレッドで 2 行ずつ足し続けながら取った 4 つのバックアップが、どれも完全で、行数が偶数ぶんの増加（途中の状態ではない）であり、バックアップの間も書き込みが進み、1 回の書き込みが `busy_timeout` に達しないこと。
- アプリ（`database.rs`）: ① `run_backup` の処理が動いている間に、アプリの接続での読み取りと書き込みが終わること（`run_backup` が Mutex を持っていると、タイムアウトで失敗する。持たせて試して、失敗することを確かめた）。② 4 万行の DB で実際に `VACUUM INTO` を行いながら保存を続け、保存の最長がバックアップの長さの半分未満で、バックアップが完全なこと。③ 復元は実行中のバックアップが終わるまで始まらず、終われば再びバックアップが取れること。④ DB を開けなかったときは保持しているエラーを返すこと。

計測（リリースビルド、この Mac の SSD。JS から 8ms ごとに `search_books`、約 0.5 秒ごとに `list_books` を呼び続け、起動の約 5 秒後に始まる日次バックアップの前後の待ちを見た。各 3 回）:

| | バックアップ（`VACUUM INTO`） | 検索の最大の待ち（ふだん 1ms） | 一覧の取り直し（ふだん） |
|---|---|---|---|
| 5,000 冊、これまで | 204〜209ms | **201〜212ms**（バックアップが終わるまで待たされた） | — |
| 5,000 冊、別の接続（0003 の DB） | 95〜103ms | **14ms** | 45〜47ms（バックアップ中に始めても 45〜49ms） |

## 理由

- 項目ごとの記録にすると、別の端末が別の項目を手で直しても記録が消えない（FR-SYNC-05）。保存形式の列は残したので、表示・書き出しのコードは単純なままである。
- 記録を書誌の項目に限ったのは、手修正の保護（FR-META-07）と取得元ごとの再取得（FR-BOOK-09）が書誌の項目にしか意味がないため。
- 派生データを `apply_op` の後処理で更新すると、ローカルの変更と他端末の Op の取り込みが同じ経路になり、取りこぼしがない。端末ローカルで、いつでも本から作り直せるので、正規化の仕様を変えても `DERIVED_VERSION` を上げるだけでよい。
- 2 文字以下を `LIKE` にするのは trigram が 3 文字未満を扱えないため。20,000 冊で全表走査しても十数ミリ秒で足りる（計測値は下記）。
- 作成を 1 つの Op にするのは、8.3 の「新規作成は全項目を set に入れた Op」に従うため。完全削除も 1 つの Op にして、他端末に同時に伝わるようにした。
- 復元で outbox を空にし、未書き出しの Op を別のテーブルに移すのは、seq のカウンタを 0 に戻す（0005 §2）と、outbox の主キーが古い行と衝突するため。捨てずに残すのは、フェーズ 2 の判断（古い端末 ID のまま書き出す、状態から作り直すなど）の材料を失わないため。
- 復元の前に今の DB を残すのは、間違えて復元しても戻せるようにするため。
- `field_clocks` を `WITHOUT ROWID` にするのは、行を持つ表と主キーの索引で同じキーを 2 回持つ無駄を省くためで、列・主キー・値、Op・HLC の形は変えないので、収束の性質（順序・重複によらず同じ状態）に影響しない。空きページが多いときだけ `VACUUM` するのは、ふつうの起動（マイグレーションなし）を遅くしないため。
- バックアップを別の読み取り専用の接続にするのは、アプリの接続を持ったまま数百ミリ秒〜1 秒の処理をすると、その間の検索・一覧・保存が待たされるため。WAL では読み取りが書き込みを止めず、書き込みも読み取りを止めない。復元だけが、ファイルを置き換えるので、重ならないようにした。

性能（`cargo test --release -p bibcontainer-core --test perf -- --ignored --nocapture`、この Mac の SSD、中央値）:

| 項目 | 5,000 冊 | 20,000 冊 |
|---|---|---|
| `list_rows`（全件） | 約 9ms | 約 38ms |
| 検索（3 文字以上、ISBN） | 0.1〜0.2ms | 0.3〜1.2ms |
| 検索（2 文字以下の LIKE） | 約 3ms | 約 14ms |
| 派生データの全体の作り直し | 約 100ms | 約 460ms |
| 本の作成（検証・Op・派生データ込み） | 1 冊あたり約 0.2ms | 同左 |

目標（5,000 冊で 100ms、20,000 冊で 300ms）を大きく下回る。

## 影響・今後

- 要件書 8.2 のスキーマ案は、`field_sources_json`・`manual_fields_json` の記述（0005 §1）に加え、`books_fts` の列（`series` を含み、`authors` にヨミを含める）、`book_idx`、`local_settings`、`outbox_restored` を反映するよう、修正を提案する。
- `outbox_restored` の未書き出しの Op をどうするかは、フェーズ 2 で決める。
- タグの名前の変更は、名前が完全に一致するタグだけにした。ツリーの親を変えたとき、子（`親/子`）も変えるかは未決。→ 0009 で、子孫もまとめて変えることにした（`rename_tag` を階層に対応させた）。
- CSV は、`=` `+` `-` `@` で始まる欄を Excel が数式と解釈しうる（取得元の書名などは信頼できない入力）。今は加工していない。対策するなら、そのような欄の先頭に `'` を付ける。→ 0009 で対応した（`=`・`+`・`-`・`@`・タブ・CR で始まる欄に `'` を付ける）。
- `pre-migration-*` と `pre-restore-*` は自動では消えない。世代の管理は、必要になったら足す。0003 の移行前のバックアップ（5,000 冊で 61MB、2 万冊で 243MB）も、そのまま残る。
- 要件書 8.2 の `field_clocks` は、`WITHOUT ROWID` にする（0003）よう、修正を提案する。
- `outbox` の書き出し済みの行を消す処理は、フェーズ 2 の同期エンジンと一緒に決める（DB の約 23%。§11）。
- `purge_books` は、手元にある取得元・手修正の記録だけを消す。別の端末が同時に付けた記録は、完全削除した本の行に残りうる（一覧にも検索にも出ない）。
- ISBN の一覧からの一括登録（FR-IO-03）、汎用 CSV の取り込み（FR-IO-04）、スマート本棚（FR-LIST-05）、再取得の画面は、このクレートの範囲外（`src-tauri` とフロントエンド）。
