# 0016: 同期のアプリへの組み込み（`src-tauri/src/sync/`、画面の差し替え）

## 状態

採用

## 背景

同期エンジン（`crates/sync`。0014）と同期の画面（`src/features/sync/`。0015。モックで動いていた）を、`src-tauri` でつなぎ、画面を本物の IPC に差し替えた。0013 §8（いつ動かすか）、0014 §11（組み込みの手順）、0015「統合時に差し替える箇所」に従った。ここには、それらでは決めていなかった細部と、実装で決めたこと（状態の組み立て、置き換え・再接続・復元の流れ、スレッドとロック）を記録する。

## 決定

### 1. 構成

| 場所 | 役割 |
|---|---|
| `src-tauri/src/sync/settings.rs` | `local_settings` の `sync` セクション（`SyncSettings`: `folder`＝`bibcontainer-library` の絶対パス、`deviceName`）。端末名の既定値はホスト名（`gethostname`）。1〜64 文字、前後の空白を除き、空は `validation` |
| `sync/db.rs` | `AppSyncDb`: エンジンの `SyncDb` を `Database` の接続の Mutex につなぐ（`Database::with_connection`。`Database::run` と同じ Mutex を、呼んだスレッドで借りる） |
| `sync/schedule.rs` | いつ動かすかの判定（純粋な状態機械。時刻は引数）と、手入れの時期の判定 |
| `sync/status.rs` | `SyncStatus` の組み立て（純粋）と、アプリが覚えている直近の結果（`Live`） |
| `sync/watch.rs` | 同期フォルダのファイル監視（`notify` 8。再帰） |
| `sync/controller.rs` | managed state の `Arc<SyncController>`。スケジューラ、周期の実行、設定・解除・置き換え・端末名・書影の整理、終了時の書き出し |
| `sync/commands.rs` | IPC コマンド 7 つ |
| `database.rs` | `with_connection`・`run_blocking`（`run` の同期版）、`reset_keeping_settings`（置き換え用の DB の作り直し） |
| `events.rs` | `emit_library_changed`（自分の変更。書き出しの合図も送る）と `emit_remote_library_changed`（他の端末から取り込んだ変更。合図を送らない） |

- コマンド（すべて async。引数のキーは camelCase）: `get_sync_status`、`inspect_sync_folder(path)`、`setup_sync(path, mode)`、`leave_sync`、`sync_now`、`set_device_name(name)`、`gc_covers`。戻り値は、`inspect_sync_folder` が `FolderInspection`、`gc_covers` が消した件数（`number`）、ほかの 5 つは操作後の `SyncStatus`（0015 の想定どおり。`api.ts` で包む必要はなかった）。
- イベント: `sync-status`（ペイロードは `SyncStatus`。変わったときだけ出す）。蔵書が他の端末の変更で変わったときは `library-changed`（`books` は変わった本、`others` は本以外）。
- エラー: `SyncError` → `AppError` は、同期フォルダの読み書きの失敗が `io`、今の状態ではできないこと（未設定、別のライブラリ、手元にデータがある、ライブラリがない・すでにある、端末 ID の重複、新しいアプリが必要、`library.json` が読めない）が `conflict`、DB の失敗はコアのエラーと同じ分け方、JSON・内部は `internal`。メッセージはエンジンの日本語のまま。
- `capabilities` と CSP は変えていない（フォルダ選択は `dialog:allow-open` が既にある。同期フォルダへの読み書きは Rust 側）。

### 2. いつ動かすか

スケジューラは 1 つのタスク（`SyncController::run_scheduler`）。合図（`Signal`）とタイマーを `tokio::select!` で待ち、`Schedule`（`schedule.rs`）に「いま何を動かすか」を聞く。動かすときは `op_lock` を取って 1 つずつ実行する（§5）。

| 契機 | 動かすもの | 細部 |
|---|---|---|
| 起動 | 起動の 1 秒後に `engine.sync()`（「スナップショットが必要」の印 → 取り込み → 書き出し）と、手入れの確認 | 同期が設定されていなければ何もしない。起動時に未書き出しがあれば、ここで書き出される |
| ウィンドウが前面に来た | 取り込み | すぐ。ただし前回の取り込みの開始から 3 秒はあける |
| ファイル監視の通知 | 取り込み | 最後の通知から 2 秒まとめる。通知が続いても、最初の通知から 10 秒で動かす |
| 60 秒ごと | 取り込み、書き出し、手入れの確認、監視の張り直しの確認 | 書き出しは、未書き出しがなければエンジンが何もしない。前の書き出しの失敗のやり直しも兼ねる。自分の変更を待っている間の定期の確認は、書き出さない（まとめ書きを崩さない） |
| 取り込みの続き | 取り込み | `remaining_files > 0` なら、すぐ次の取り込みを予約する。1 回の周期で続けて取り込むのは 5 ラウンド（1 ラウンド 200 ファイル）まで |
| 自分の変更 | 書き出し | 最後の変更から 5 秒後。**変更が続いても、最初の変更から 30 秒で書き出す**（0013 の「最後の変更から 5 秒後」に、上限を足した） |
| 終了 | 書き出し | `RunEvent::ExitRequested` で終了を止め、最大 5 秒で書き出してから、あらためて終了する（2 回目の要求は止めない）。同期が未設定なら、止めずにそのまま終了する。5 秒で終わらなければあきらめる（書き出しは途中で止まっても、次の起動でやり直せる） |
| バックアップの復元のあと | `engine.sync()`（別のタスクで） | 復元した DB は新しい端末 ID と「スナップショットが必要」の印を持つので、先にスナップショットを書き、古い端末 ID の変更と他の端末の変更を取り込み直す。設定の確認と監視の張り直しもする |
| 手入れ（`maintain`） | 古い一時ファイルの掃除、自分のセグメントの統合 | 起動時の周期と 60 秒ごとの周期で、前回から 20 時間以上たっていれば。時刻は `local_meta` の `sync_last_maintain_ms`（壁時計。時計が戻ったら走らせる）。失敗しても、次は 20 時間後 |

- 「自分の変更」の合図は、`events::emit_library_changed` から送る（データを変えるコマンドと、書誌取得の自動再取得が呼ぶ）。取り込んだ変更を知らせる `library-changed` は `emit_remote_library_changed` で出し、書き出しの合図を送らない。
- 取り込みのあと、`ImportReport` の `changed_book_ids`・`other_changed` を `library-changed` で知らせる（変わったものがあるとき）。
- **ファイル監視**（`watch.rs`）: ライブラリのフォルダを再帰で監視する。次の通知は取り込みのきっかけにしない: 読み取り（Access）、自分の `ops/<自分>`・`snapshots/<自分>`・`devices/<自分>.json`、`.` で始まる名前（書き込み途中の `.tmp-*` を含む）、`desktop.ini`・`Thumbs.db`、`covers/`（書影は、それを参照するセグメントが届いたときの取り込みで写す。自分の書影の写しが大量の通知になるのを避ける。あとから届いた書影は、60 秒ごとの取り込みで拾う）。macOS の FSEvents は実パスで通知するので、実パスの接頭辞も照合する。フォルダがない（Drive 未接続）ときは監視できず、60 秒ごとの周期で張り直しを試す。設定・解除・復元のあとにも張り直す（端末 ID が変わるので、自分の書き込みの見分けも直る）。Google Drive のストリーミング（仮想ドライブ）は通知が届かないことがあるので、60 秒ごとの取り込みを続ける。

### 3. 状態（`SyncStatus`）の組み立て

`status.rs` の純粋な関数 `build_status`。入力は 3 つ。

1. 手元の DB から数えられる値（`engine.local_counters()`: ライブラリ ID・端末 ID・未書き出しの Op・届いていない書影）。
2. 端末ごとの設定（`sync` セクション: フォルダ、端末名）。
3. アプリが覚えている直近の結果（`Live`）: 最終の取り込み・書き出しの時刻、失敗、取り込みの一部のエラー、時計のずれ、同期フォルダにいる端末の一覧。

- **設定済み**は、DB にライブラリ ID があり、かつ設定に同期フォルダがあるとき。**どちらかがなければ `disabled`**（同期フォルダを選び直すと、同じライブラリなら「再接続」になる。§4）。
- 状態は、`syncing`（取り込み・書き出しが 500 ミリ秒より長引いたとき、または「今すぐ同期」の間。短い処理で毎回ちらつかせない。設定の最中は出さない: 画面が設定済みの表示に切り替わってしまうため）> 失敗（`error`・`mismatch`・`updateRequired`）> `idle`。
- 失敗は、取り込み側と書き出し側の 2 系統で覚える。それぞれ、次にその側が成功したときだけ消える（取り込みが失敗した周期では、書き出さない。書き出しが何も書かずに成功しても、取り込みの失敗は消えない）。画面に出すのは、重い方（不一致・更新が必要を、ふつうのエラーより先に）。メッセージが前と変わったときだけ、警告をログに出す。
- 取り込みは続けられたが一部でエラーがあったとき（ファイルを読めない、書影を写せない）は、状態は `idle` のまま、`error` に「…（ほか N 件）」を出す。
- 時計のずれは、取り込みで見つかったら覚え、新しいものが見つかるまで残す（設定・解除で消える）。
- 同期フォルダにいる端末の一覧（`devices()` は同期フォルダを読む）は、取り込みで何か適用したとき・書き出したとき・一覧が空のとき・前回から 5 分以上たったとき・設定したときに読み直して覚える。最終の書き出しは、覚えている時刻、なければ一覧の自分の記録。端末名を変えたときは、一覧の自分の行も直す。
- `sync-status` は、状態が前に送ったものと変わったときだけ出す。自分の変更の合図のたびに状態を作り直して（未書き出しの件数を伝える）送るが、100 ミリ秒まとめる。
- 同期フォルダが使えないとき（Drive 未接続、権限、容量不足）は、状態を `error` にして原因を出す。ローカルの操作は止めない（DB の接続は、エンジンが短い処理のたびに借りるだけ）。

### 4. 設定・解除・置き換え・再接続・復元の流れ

**`inspect_sync_folder(path)`**: `LocalFolder::resolve_root(path)` で `bibcontainer-library` の場所を決め（絶対パスだけ受け付ける。相対は `validation`）、`engine.inspect(その絶対パス)`。何も残さない。

**`setup_sync(path, mode)`**（`op_lock` を取って実行）:

1. `create`・`join`・`joinMerge`: そのまま `engine.setup(mode)`。成功したら、`sync` セクションに `bibcontainer-library` の絶対パスを保存し、`Live` を作り直し、端末の一覧を読み、`library-changed`（取り込みで変わったものがあれば）と `sync-status` を出し、続けて取り込みの周期を予約する。
2. **同じライブラリを別のパスで選び直した**（フォルダの `libraryId` が手元のライブラリ ID と同じ。Windows のドライブ文字が変わった、設定が途中で止まった、など）: エンジンの `setup(Join)` が、取り込み済みの範囲と印を引き継ぎ、スナップショットを書かず、取り込み直す（0014 §8。手元にデータがあっても `LocalHasData` にならない。`crates/sync/tests/engine.rs` の `choosing_the_same_library_at_another_path_…` で、`Join`・`JoinMerge`・`JoinReplace` のどれでも同じに動くこと、新しい場所へ書き出せることを確かめた。エンジンは直していない）。画面は「再接続」として `join` を送る。`joinReplace` を頼まれても、同じライブラリなら DB は作り直さず、同じ扱いにする。
3. **手元が別のライブラリに属しているのに空のフォルダを選んだ**（`kind: "empty"`・`localLibraryId` が非 null）: `create` はエンジンが `AlreadyInLibrary`（`conflict`。「先に同期を解除してください」）で、何も書かずに断る。画面は新規作成を出さず、「先に同期を解除してください」と案内する。
4. **置き換え（`joinReplace`）**: まず `engine.inspect` で、参加できるフォルダか確かめる（ライブラリがない・別のライブラリ・書き込めない・更新が必要は、DB に触れずに `conflict`）。そのうえで `Database::reset_keeping_settings(バックアップの保存先)`: 接続の Mutex と `backup_gate` を取ったまま、(a) 今の DB を手動バックアップ（保存先は設定の `backup.directory`、なければ既定。バックアップに失敗したら何も変えない）、(b) `local_settings` の全行を読む、(c) 接続を閉じる、(d) 新しい DB を別のファイル（`library.sqlite3.reset-tmp`）に作り（新しい端末 ID）、(e) 設定の全行を入れ、(f) 古い WAL を消して名前を変えて置き換える、(g) 開き直す（結果によらず開き直す。復元と同じ）。そのあと `engine.setup(Join)`。**`local_settings` の行は全部引き継ぐ**（スキャン・表示・一覧・価格・バックアップ・取得元・同期の設定）。API キーは OS のキーチェーンなので影響しない。書影のフォルダ（`covers/`）はそのまま（使われなくなった分は、書影の整理で消せる）。作り直したあとは、設定が成功しても失敗しても `library-changed`（`books: []`、`others: true`）を出す（画面は `reloadLibrary` で全部取り直す）。
5. **設定の途中で失敗したとき**（取り込みの途中など）: エンジンは参加を記録したあとで取り込むので、記録が増えていれば（`library_id` が変わっていれば）、同期フォルダも保存して、状態を `error` にする。次の同期が続きから行う（画面にはエラーを返す）。参加の記録が変わっていなければ、何も覚えない。

**`leave_sync`**: `bibcontainer_sync::leave`（ライブラリ ID・取り込み済みの範囲・印を消す。同期フォルダに触れない）→ 設定の `folder` を消す（端末名は残す）→ `Live` を消す → 監視をやめる。手元のデータと同期フォルダの中身はそのまま。どこかで途中で止まっても、ライブラリ ID がなければ `disabled` なので矛盾しない。

**`set_device_name(name)`**: 検査（`validation`）→ 設定に保存 →（設定済みなら）`write_device_file(None)`。書けなければ警告を出して続ける（次の書き出しで直る）。未設定のときも変えられる。

**`gc_covers`**: 設定済みなら、先に取り込む（参照している本が届いていないと、使われている書影を消してしまうため）。取り込めなければ（`Err`）整理しない。そのあと `engine.gc_covers()` で、`local_removed + remote_removed` を返す。未設定なら手元だけ整理する。

**バックアップの復元（`restore_backup`）**: `op_lock` を取ってから `Database::restore` する（取り込み・書き出しの途中の DB を入れ替えない）。終わったら、`library-changed`（`others: true`）を出し、`after_restore`（別のタスク）で設定の確認・監視の張り直し・`engine.sync()` をする（`needs_snapshot` の印が立っているので、先にスナップショットを書く）。復元した DB の設定・ライブラリ ID は DB の中身なので、バックアップの時点のものになる（同期を始める前のバックアップなら、未設定に戻る。復元前の DB は `pre-restore-…` に残る）。

### 5. スレッドとロック

- エンジンの呼び出しは、すべて `spawn_blocking` の中（同期フォルダの読み書きと、DB の接続の借用はブロックする）。
- **同時に 2 つ動かさない**: 取り込み・書き出し・設定・解除・端末名・手入れ・書影の整理は、`op_lock`（`tokio::sync::Mutex`。待つ順は先着順）を取って 1 つずつ実行する。バックアップの復元も `exclusive()`（同じロック）を取る。`inspect_sync_folder` と `get_sync_status` は、ロックを取らない（読み取りだけ）。
- DB の接続: エンジンは、同期フォルダの読み書きの間は持たず、短い処理のたびに `Database` の接続の Mutex を借りる（`AppSyncDb::with_conn` → `Database::with_connection`）。同期が長引いても、画面の操作は待たされない。復元・置き換えは、同じ Mutex を持ったままファイルを入れ替えるので、その間エンジンは待たされ、終われば新しい接続で動く。取る順は、`op_lock`（async）→ 門（`backup_gate`）→ 接続の Mutex。接続の Mutex を持ったまま、`op_lock` を待たない。
- `Live`・最後に送った状態・ファイル監視は、短く持つ `std::sync::Mutex`（持ったまま `await` や DB・ファイルの操作をしない）。
- `Hooks`（状態を送る関数、蔵書の変更を知らせる関数）をコントローラに渡す形にして、コントローラは Tauri のランタイムに依存しない（本番は `app.emit`、テストは MockRuntime の `app.emit`）。

### 6. 画面の差し替え（0015 の一覧のとおり）

- `src/features/sync/types.ts`: `SyncStatus` など 7 つの型を `src/bindings/` の再エクスポートにした（`SyncApi` はそのまま。形は暫定の型と同じで、手直しは要らなかった）。
- `src/lib/ipc.ts`: `CommandMap` と `ipc.*` に 7 コマンド、`onSyncStatus` を足した。
- `src/features/sync/api.ts`: `selectBackend()` を `inTauri() ? ipcSyncApi : mockSync.api` にした。開発用パネル（`SyncDevPanel`）は、これまでどおり開発ビルドのモックで動いているときだけ出る（Tauri の中では出ない）。
- `setupPlan.ts` と `SyncSetup.tsx`: 手順に `reconnect`（同じライブラリの選び直し。「この場所に付け替える」。`join` を送る）と `leaveFirst`（手元がライブラリに属しているのに空のフォルダ。新規作成を出さず、「同期を解除してから、選び直す」）を足した。手元が別のライブラリのときの `library` の判定（エンジンは `otherLibrary` を返すはず）は、念のため `otherLibrary` と同じ扱い。
- モック（`mockSync.ts`）: エンジンと同じく、`empty` で手元がライブラリに属していれば `create` を `conflict` で断り、同じライブラリの選び直しは `join` だけ受け付ける。開発用パネルに「この端末が属しているライブラリ」の切り替えを足した。
- テスト: Tauri の中を模したテスト（`App.test.tsx`・`SettingsScreen.test.tsx`・`SyncSection.test.tsx`）は、`src/test/syncIpc.ts` で、同期のコマンドと `sync-status` を、モックの同期につなぐ（IPC の層を通して、状態はモックが決める）。

### 7. テスト

- 純粋な関数: `schedule.rs`（書き出しのまとめ 5 秒・上限 30 秒、監視の 2 秒・上限 10 秒、前面に来たときの間隔、定期の確認、手入れの時期）、`status.rs`（状態の決め方、失敗の 2 系統、一部のエラー、時計のずれ、一覧の更新）、`settings.rs`（端末名の検査、保存の往復）、`watch.rs`（通知の振り分け。実際の監視で、他の端末のファイルの通知は届き、自分の書き込みは届かないこと）。
- `AppSyncDb`（`db.rs`）: `Database::run` と同じ接続を借りる、DB を開けていないときのエラー、接続を借りている間は待たされる。
- `Database::reset_keeping_settings`: バックアップ、新しい端末 ID、設定の引き継ぎ、作業用ファイルが残らないこと、再起動後も新しい端末 ID、バックアップに失敗したら何も変えない、DB を開けていなければ断る。
- コマンド（`sync/tests.rs`。`commands/ipc_tests.rs` の `Harness` で、フロントが送るのと同じ JSON の引数から呼ぶ）: 未設定の状態、`inspect`（何も作らない、相対パスは `validation`）、設定・解除・統合・置き換え・再接続・空のフォルダでの新規作成の拒否、置き換えが DB に触れずに断る場合、置き換えの途中で失敗しても画面を取り直して次の同期が続きから行うこと（Unix のみ）、端末名、同期フォルダが使えないとき（状態が `error`、ローカルは動き、つながれば戻る）、ライブラリの不一致、書影の整理、終了時の書き出し、復元のあとの再開、復元のロック。
- **2 つのアプリを模した結合テスト**: `Harness` を 2 つ（別々の一時フォルダの DB）と 1 つの同期フォルダで、`create_book` → 書き出し（スケジューラが 5 秒後に行うのと同じ `run_due`）→ もう一方で取り込み（`run_due`）→ `list_books` に出て `library-changed` が届く。逆向きは `sync_now` で。
- エンジン（`crates/sync/tests/engine.rs`）: 同じライブラリのコピーを別のパスで選び直す（`Join`・`JoinMerge`・`JoinReplace`）、空のフォルダでの新規作成を断って何も書かない（解除すれば作れる）。
- フロント: `planSetup` の新しい分岐、`SyncSection` の再接続・先に解除、モックの新しい規則、`api.ts` の選択（Tauri の中・外）、`ipc.ts` の 7 コマンドと `sync-status`。
- Windows で落ちやすいテストへの対応: 絶対パスは `tempfile`、監視しているフォルダを含むフォルダの名前変更は、先に監視をやめてから（`drop_watcher`。テスト専用）、`chmod` を使うテストは Unix のみ。

## 理由

- 状態を「手元の DB の数」「設定」「覚えている直近の結果」から純粋な関数で作るのは、状態の決め方（同期中・失敗の優先・一部のエラー・未設定）を、DB も同期フォルダもなしでテストするため。設定済みの条件を「ライブラリ ID と同期フォルダの両方」にしたのは、設定の途中で止まった（参加の記録だけが残った）端末を、画面の「再接続」に導くため。
- 取り込みと書き出しを別々の周期にしたのは、前面に来たとき・監視の通知では取り込みだけ（自分の書き出しのまとめ書きを崩さない）、定期の確認では両方（書き出しの失敗のやり直し）、と使い分けるため。書き出しに上限（30 秒）を足したのは、連続して編集していても、他の端末に届くのが遅れ続けないようにするため。
- 失敗を取り込み側・書き出し側の 2 系統で覚えるのは、片方の成功が、もう片方の失敗を隠さないため（取り込みが失敗した周期では書き出さないので、書き出しの「何も書かなかった成功」が取り込みの失敗を消さない）。
- 置き換えの前に参加できるフォルダか確かめるのは、DB を作り直したあとで断ると、手元が空になる（バックアップには残るが、利用者の驚きが大きい）ため。
- 設定の途中の失敗でもフォルダを覚えるのは、エンジンが「参加を記録してから取り込む」ので、続きから行える状態を、画面の「未設定」に戻してしまわないため。
- `covers/` の通知を取り込みのきっかけにしないのは、書影の写し（最初の同期で数千個）が、自分の書き込みでも他の端末の書き込みでも大量の通知になり、取り込みを繰り返し起こすため。書影を参照するセグメントが届けば取り込みが走り、遅れた書影は 60 秒ごとの取り込みで拾える。

## 影響・今後

- **要件書の修正を提案する**（直接は直さない）: FR-SYNC-07 に「最初の変更から 30 秒たてば書き出す（連続した編集で、他の端末への反映が遅れ続けない）」を足す。FR-SYNC-09 に、同じライブラリを別のパスで選び直したときは「再接続」（場所だけ付け替え）、手元がライブラリに属しているのに空のフォルダを選んだときは新規作成を断る、を足す。
- **未解決・注意**:
  - **同期フォルダの場所が使えなくなったとき（Windows のドライブ文字が変わった、など）の付け替えの導線**: 設定済みの画面（`SyncConfigured`）には、フォルダを選び直すボタンがない。今は「同期を解除 → フォルダを選び直す」で復旧する（手元にデータがあるので「統合」になる。同じライブラリなら ID が同じなので、本は 2 冊にならないが、画面は「同じ本が 2 冊になることがあります」と案内する）。「再接続」の手順は、設定の途中で止まった（参加の記録だけが残り、フォルダの設定がない）ときに出る。設定済みの画面に「フォルダを選び直す」を置く案がある（選んだフォルダが同じライブラリなら、解除せずに `join` で付け替える。モックの `setupSync` は、設定済みでの再設定を `conflict` で断るので、あわせて直す）。
  - 書影があとから届いても（取り込みが写しても）、`library-changed` は出ない（本の行が変わっていないため）。一覧の書影は、再表示で出る。届いていない書影の数は、状態に出る。
  - 取り込みが長くかかる（Drive のストリーミングで読み取りが固まる）と、`op_lock` を待つコマンド（解除・端末名・書影の整理・復元）も待つ。読み取りに時間切れはない（0014 の上限は、1 回の取り込みのファイル数だけ）。
  - 時計のずれは、新しいずれが見つかるまで残る（他の端末が時計を直しても、その端末の新しい変更を取り込むまで消えない）。
  - 実機（Google Drive を使った Mac と Windows の間）での確認は未実施。ファイル監視の通知が、Drive for desktop のストリーミング・ミラーリングで届くか、Windows（ReadDirectoryChangesW）で届くかは、実機で見る。
  - 終了時の書き出しが 5 秒で終わらなかったときは、次の起動でやり直す（`flushed` にする前に落ちても、同じ内容で書き直す。0014 §6）。
  - 置き換えのあと、使われなくなった書影が手元に残る。「使われていない書影を整理」（30 日より前のもの）で消せる。
