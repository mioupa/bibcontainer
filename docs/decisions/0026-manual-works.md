## 背景

0022 §1 の 8 番目。巻をまとめた表示（0024）は、巻次を外した書名と著者（1 人以上が共通）で作品を判定する。この判定では、特装版・アンソロジー・書名の表記が違う巻などがまとまらず（判定もれ）、同名・同著者の別の作品がまとまる（判定の誤り）ことがある。そこで、本ごとに「作品」を手で上書きできるようにした。

0022 で決まっていたこと: 自動の判定より優先する、本ごとの上書き。一覧で本（畳んだ作品の行なら、その全巻）を複数選び、右クリックの「1 つの作品にまとめる」「作品から外す」「自動に戻す」。上書きは books の新しい項目（新しい番号のマイグレーション、`record_change` で変え、同期で他の端末に届く、書き出しにも出す）。手動の作品の表示名は自動と同じ（名前を付ける機能は作らない）。同期で食い違うときのふるまいは、このセッションで決める。

## 決定

### 1. データ（books の `work_id`）

- `0004_book_work.sql` で books に `work_id TEXT`（NULL 可）を足した。Op の項目名も `work_id`。値は次の 3 通り。

| 値 | 意味 |
|---|---|
| NULL | 自動（0024 の判定。§2 の規則 3・4） |
| `"none"` | どの作品にも入れない（「作品から外す」） |
| それ以外 | 手動の作品の ID。同じ ID の本が 1 つの作品。新しく作るときは UUIDv7 |

- 利用者が持つ項目として扱う（`memo`・`location_id` と同じ）。取得元・手修正の記録（`field_sources`・`manual_fields`）は付けない。検索の派生データにも入れない。
- ローカルの変更の検証（`canonical_book_value`）: null、`"none"`、ID の書式（UUID）だけを受け付ける。空文字と空白だけは null。作品はエンティティではないので、ID が使われているかは確かめない。他の端末から届いた値は、文字列なら何でも受け入れる（`"none"` 以外は手動の作品の ID として扱う）。
- ゴミ箱に移しても値は残る（戻すと作品に戻る）。完全削除では、ほかの項目と同じく既定値（NULL）に戻る。
- 一覧の行（`ListRow`）と詳細（`BookDetail`）に `workId` を足した。
- 書き出し: CSV は `巻次（並べ替え用）` の次に `作品（手動）` の列を足した（空＝自動、`まとめない`、手動の作品の ID）。JSON は `Entity::Book.fields()` から作るので、何もしなくても `work_id` が出る。
- **古い版の端末**: 届いた `work_id` は、知らない項目として `extra_json` に入り、時計（`field_clocks` の `work_id`）は LWW で進む（0004）。0004 のマイグレーションは、`extra_json` の `work_id`（文字列か null）を列に移し、キーを除く。時計はそのまま使う（0004「影響・今後」の手順。`extra_json` から列に移した最初の例）。同期の形式（Op・スナップショットの版）は変えていない。

### 2. まとめ方（`src/features/library/grouping.ts`）

「巻をまとめる」がオンのとき、表示中の本（絞り込み・検索・並べ替えのあと）を、次の規則でまとめる。

1. `"none"` の本は、どの作品にも入らない（普通の行）。
2. 手動の作品の ID が同じ本は、書名や著者が違っても、同じ作品。
3. 上書きのない本どうしは、0024 §5 の規則でまとめる（自動の作品）。
4. 自動の作品（1 冊だけのものも）が、手動の作品の本と「比べるための書名が同じで、著者が 1 人でも共通」なら、その手動の作品に入る。つながる手動の作品が 2 つ以上なら、どれにも入らない（自動の作品のまま）。著者のない本は、手動の作品とはつながらない。
5. 違う手動の作品どうしは、書名と著者が同じでも、まとめない。

- 2 冊以上の作品だけを畳むこと、表示名（作品の中でいちばん前の巻の、巻次を外した書名）、作品の置き場所、作品の中の順、畳んだ行の表示は、0024 のまま。
- 手動の作品の鍵は `work:` ＋ 区切り（`\u001f`）＋ 手動の作品の ID。自動の作品の鍵（`work:` ＋ 比べるための書名 ＋ 区切り ＋ 著者）は書名が空でないので、重ならない。
- 「巻をまとめる」がオフのときは、上書きも使わない（すべて普通の行）。

### 3. 操作（右クリックのメニュー）

- 「巻をまとめる」がオンのときだけ、「CSV に書き出し…」のあとに区切りを入れて、「1 つの作品にまとめる」「作品から外す」「自動に戻す」を出す。
- 対象は、選んだ表示の単位を本に広げたもの（`expandToBookIds`。作品の行なら、表示中のその全巻）。
- **1 つの作品にまとめる**（対象が 2 冊以上のとき押せる）: コアの `merge_works`（コマンドも同じ名前）。1 つのトランザクションで、
  1. 対象（重複を除き、完全削除した本は除く）が 2 冊未満なら `Validation`。
  2. 対象の今の `work_id` から、手動の作品の ID を集める。
  3. ID が 1 つもなければ、新しい ID（UUIDv7）を作る。あれば、ライブラリ全体（ゴミ箱の本を含み、完全削除を除く）で冊数がいちばん多いものを使い続ける（同じ冊数なら、文字列として小さい ID）。
  4. 対象と、2 で集めた ID の本すべて（絞り込みで隠れている本、ゴミ箱の本も含む）を、その ID にする。値が変わる本だけ Op を書く。
  5. 使った ID と、書き換えた本の ID を返す。アプリは `library-changed` を出す。
- **作品から外す**: 対象を `"none"` にする（今の一括変更 `update_books` で `work_id` を書く）。対象の中に `"none"` でない本があれば押せる。
- **自動に戻す**: 対象の `work_id` を null にする（同じく `update_books`）。対象の中に上書きのある本があれば押せる。
- 結果はトーストで知らせ、何も変わらなければ「変更はありませんでした」。
- 操作のあとの選択: まとめたら、その作品の行を選ぶ（畳んだまま）。外す・戻すのあとは、対象の本を選ぶ。
  - アプリでは、行の更新が `library-changed` で遅れて届く。そこで、操作が済んだら `selectionStore` に「保留中の選択」（`pendingWork`。期待する `work_id`、対象の本、まとめたときは作品の行の鍵、期限 10 秒）を置き、`useGroupedList` の layout effect が、表示中の対象の本がすべて期待する値になったときに選ぶ（`resolvePendingWork`。純粋関数）。作品の行が並びになければ（絞り込みで 1 冊以下）、表示中の対象の本を選ぶ。対象が 1 冊も表示されていないか、期限を過ぎたら、選ばずに捨てる。利用者が選び直したら（クリック・矢印・⌘A・検索欄の ISBN・選択の解除）取り消す。
  - 0024 §7 の「畳んだ作品の中の本に focus が来たら、その作品を開く」は、保留中の選択の対象の本には効かせない（まとめる前の focus がアンソロジーなどにあると、まとめた作品が開いてしまうため）。
  - まとめて何も変わらなかったとき（すでに 1 つの作品）も、作品の行を選ぶ。外す・戻すで何も変わらなかったときは、選択に触らない。
- **2 つの作品に分けるとき**（自動で 1 つにまとまる本、または手動の作品を、2 つにする）: 片方の組を選んで「作品から外す」→ その組を選んで「1 つの作品にまとめる」→ 残りの組を選んで「1 つの作品にまとめる」。規則 5 で、2 つの手動の作品は、書名と著者が同じでもまとまらない。分けたい本が 1 冊なら、「作品から外す」だけでよい。

### 4. 同期で食い違ったとき

- 上書きは本ごとの 1 項目なので、項目ごとの LWW（0004）で、Op がどの順で届いても、全端末で同じ値になる（収束の性質テストに `work_id` を入れた）。まとめ方（§2）は、行の値と表示中の本だけで決まる純粋関数なので、同じ絞り込みなら、どの端末でも同じ形に見える。
- 食い違ったときは、本ごとに、あとの操作（HLC が新しい方）が勝つ。

| 同期の前に、2 台でしたこと | 同期のあと（両方の端末で同じ） |
|---|---|
| A で {1, 2, 3} を、あとで B で {2, 3, 4} をまとめた | {2, 3, 4} が B の作品。1 は A の作品に 1 冊で残り、普通の行で出る（規則 5 で、B の作品にはつながらない）。1 と 2 を選んでまとめ直せば、1 が B の作品に入る（冊数の多い B の ID を使い続ける） |
| A でまとめ、B で同じ本を外した・自動に戻した | その本は、あとの操作の値 |
| A で新しい巻を登録し、B でその作品をまとめた | 新しい巻は上書きなしのまま、規則 4 で、その作品に入る |
| A で手動の作品の本をゴミ箱に移した | 上書きは残る。戻すと作品に戻る |

- 重なる本を 2 台で別々にまとめたときに、作品が分かれうるのは、手動の作品を本の項目だけで持つため（作品を別のエンティティにしないため）。2 台で同時に作品をまとめることはまれで、分かれても、まとめ直せば直る。

## 理由

- **手動の作品にも、上書きのない本は自動の判定で入れる（規則 4）**: 0022 の「自動の判定より優先する」は、上書きのある本では、上書きが自動の判定より優先する、と読んだ。手動の作品が自動の本を受け入れないと、あとで登録した巻（`スローループ 9` など）を、毎回手でまとめることになる。指示文から補った点として、ユーザーに案を見せて承認を得た。
- **違う手動の作品どうしをまとめない（規則 5）**: 規則 4 だけだと、書名と著者が同じ本を 2 つの作品に分けられない。手で分けたものは、分けたままにする。
- **つながる手動の作品が 2 つ以上なら、どれにも入れない**: どちらに入れるかを決める手がかりがない。0024 の「著者のない本は、同じ書名の作品が 1 つだけならそこに入れる」と同じ考え方。著者のない本を手動の作品につなげないのは、書名だけで別の作品につながるのを避けるため（著者のない本はまれで、手でまとめられる）。
- **まとめるとき、対象の手動の作品を全冊ごと 1 つにする**: 0022 の「選んだ本を同じ作品にする」だけだと、手動の作品の巻を 1 冊だけ選んで別の本とまとめたときや、絞り込みで巻が隠れているときに、作品が 2 つに割れる。作品の行を選んだときと、巻を 1 冊選んだときで結果が同じになる。これも指示文から補った点で、承認を得た。自動の作品の隠れている巻には書かない（規則 4 で、絞り込みを外すと同じ作品に入る）。
- **冊数の多い ID を使い続ける**: 書き換える本（Op）が少なくて済む。新しい ID にしないので、他の端末が同時にその作品に足した本も、作品に残る。
- **外す・戻すを `update_books` にした**: 対象の本の 1 項目を書くだけなので、新しいコマンドは要らない。まとめるだけは、ライブラリ全体の本を見るので、コアの関数にした。
- **メニューを「巻をまとめる」がオンのときだけ出す**: オフのときは、まとめた結果が見えない。
- **1 項目にした**: 「自動・外す・手動」と ID を別の項目にすると、2 台で別々に変えたときに組み合わせが崩れる（「外す」なのに ID がある、など）。1 項目なら LWW で必ず意味のある値になる。

## 影響・今後

### 実装とテスト

- コア: `crates/core/src/library/works.rs`（`merge_works`、`WORK_NONE`、`MergeWorksResult`）、`validate.rs` の `work_ref`、`0004_book_work.sql`。テストは `crates/core/tests/works.rs`（まとめる規則、`update_books` での外す・戻す、検証、完全削除）、`migrate.rs`（`extra_json` からの移し替え、壊れた `extra_json` でも止まらない）、`export.rs`（CSV の列）、`convergence.rs`（`work_id` を含む収束）。
- 0004 を足したので、今のコード（`library`・`dump_canonical`・`apply_op`）は `work_id` の列を読み書きし、版 2・3 の DB には使えない。0003 のマイグレーションのテスト（`migrate.rs`）は、古い版の状態を SQL で直接作り、`dump_canonical` の代わりに books の全行と時計の全行を比べる形に直した（確かめる中身は同じ）。
- アプリ: コマンド `merge_works`（`library-changed` の `others` は false）。外す・戻すは `update_books`（`work_id` はタグ・シリーズに触れないので `others` は false）。
- 画面: `grouping.ts`（§2。手動の本がないときは、0024 と同じ処理の道筋）、`ListContextMenu.tsx`、`actions.ts`（`mergeWorks`・`setWork`）、`selection.ts` と `selectionStore.ts`（`pendingWork`）、`useGroupedList.ts`。モック（`src/dev/mockBackend.ts`）にも Rust と同じ規則の `mergeWorks` を置いた。`mockRows.ts` は、上書きのない行の中身を変えずに、別の乱数で約 2% を手動の作品（2〜5 冊。別の作品の巻を混ぜる）、約 1% を `"none"` にした。
- 性能（`perf.test.ts`、2 万行、7 回の最速、開発機の Mac）: 計算済み 8.0ms、全行が新しい 25ms、上書きのない行だけ 6.5ms（0024 では 8.9ms・24.2ms）。

### あとでやってもよいこと

- 詳細ペインに、作品の上書きの状態（自動・外した・手動の作品）を出す。今は、外した本と、自動で 1 冊だけの本の見分けがつかない（「自動に戻す」が押せるかどうかで分かる）。
- 作品に名前を付ける（0022 で作らないと決めた）。
- 汎用 CSV 取り込み（0022 §1 の 6）で、`作品（手動）` の列を読む。
